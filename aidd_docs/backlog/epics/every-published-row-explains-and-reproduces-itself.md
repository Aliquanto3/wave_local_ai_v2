# Epic: Every published row explains and reproduces itself

Given any published benchmark row, a client's engineer can read from the row alone how it was produced — sampling, rendered prompt and template version, generation caps, hardware fiche hash, roster entry, code sha, energy method and emission factor, cost basis — and re-run it to an explicit reproduced / not-reproduced verdict.

## Context and Value

The audience is the client-side engineer the PRD names as one of the two audiences a result must survive: the one "auditing methodology and reproducibility" (PRD, Problem Statement). That engineer does not read the repo's docs first; they read a row. Today a row does not answer them.

Verified current state, at `a2ffe37`:

- **Runtime is single-shot.** One measurement per configuration, so no N, no mean, no standard deviation, no spread, and nothing to compare a re-run against. The audit records this as the open half of E10: "quality side done (pinned sampler, reproduced twice, evidence committed); runtime side single-shot, no spread" (`2026_08_21_expectations-gap-audit/audit-and-plan.md`, section 5.2).
- **The fiche is not an identity.** Its fields are flattened inline into every runtime row (`aidd_docs/results/runtime-reference.jsonl`) with no content hash, so no row can be invalidated when the fiche behind it changes, and two rows from different machines are distinguishable only by eye.
- **The machine is hardcoded, not declared.** `N_CPU_MOE = 37` and `THREADS = 8` (`src/wave_local_ai_v2/server.py:26,29`), `LLAMA_CPP_BUILD = "b10537"` (`src/wave_local_ai_v2/__init__.py:25`) and the model file are constants. A row therefore reports a build string the code asserts rather than one the running binary reported, and the project cannot be re-run on a second machine without editing source — the audit's E11.
- **Carbon is computed and thrown away.** `energy.py` returns `energy_kwh` and `energy_method` only; CodeCarbon's emissions figure, the region and the emission factor that converts between them are discarded. The audit's E3.
- **And the method label it does keep is derived from the wrong channel.** `energy.py:52-55` sets `energy_method` from the GPU channel alone (`"measured_nvml" if data.gpu_energy and data.gpu_energy > 0 else "estimated_tdp"`) while returning `data.energy_consumed`, CodeCarbon's CPU plus GPU plus RAM total. Both tracked runtime rows are therefore published `measured_nvml` over a figure whose largest component — 37 of 40 MoE layers running on CPU — is a TDP estimate that `architecture.md` Gotchas warns "can be off by a factor of 2-3 on a laptop under thermal throttling".
- **Provenance is partial.** `quality_cli.py` writes `run_id` and `captured_at`; neither row type carries the release version or commit sha, and *both* tracked reference files predate even `run_id` — `grep -c run_id aidd_docs/results/quality-reference.jsonl` returns 0 across its 40 rows, so the two quality runs behind the reproduced-twice claim cannot be told apart inside the committed file.
- **There is no roster file**, so no row cites a pinned repo revision, checksum, quant, licence or per-model flag set — and the "a dense model takes no MoE-offload flags" rule of Methodology 13 has nowhere to live. This is what makes the audit's E6 spec-only.
- **A row does not record the call path that produced it, so its prompt field has no stable meaning.** Both CLIs post to llama-server's raw completion endpoint — `POST /completion` (`src/wave_local_ai_v2/__init__.py:202`, `quality_cli.py:146`), not `/v1/chat/completions` — which takes `prompt` verbatim and applies no chat template. `--jinja` (`server.py:62`) governs the chat endpoint, which nothing calls. Today's stored string is therefore byte-identical to what was sent; the gap is that no row carries the endpoint, a template id or a template content hash, so a row written before the chat-endpoint migration (owned by `no-use-case-is-silently-absent`) is indistinguishable from one written after it, when the stored string stops being the bytes the model received.
- **The classification suite carries no language and no provenance tag**, and holds 10 items against Methodology 4's 20 (`src/wave_local_ai_v2/classification_suite.py`).

Two Methodology criteria in this area are already satisfied and are recorded here as done rather than as work: **12, cloud model pinning** (the dated Mistral model id is recorded and a run refuses to start when it is absent from the provider's live model list, shipped via `2026_08_21_mistral-model-preflight/`) and the **quality half of 1, sampling determinism** (seed, temperature, top_p, top_k and presence penalty are pinned and written into every quality row's `sampling` block, shipped via `2026_08_21_quality-sampling-reproducibility/`, reproduced twice). The reproduction was real but is not readable from the committed file, which carries no `run_id`; the regenerated quality reference carries one per row so the claim is checkable from the artifact rather than from the shipping task.

The value is the product's founding bet. The PRD's defensibility claim is not that the numbers are good; it is that a challenger can check them. Every criterion below exists so a published number can be *failed*. Without them the runtime table fails the project's own memory's test of a publishable number: "Runtime metrics are NOT reproducible across machines. Every result row must carry its hardware fiche (CPU, RAM, GPU, driver, llama.cpp build, quant, flags). A number without a fiche is meaningless" (`aidd_docs/memory/architecture.md`, Gotchas) — and a number that cannot be failed is worth less in front of a sceptical engineer than no number at all.

## Boundaries

- Includes: the runtime half of criterion 1 (sampling recorded on runtime rows too); 2 prompt parity and versioning; 3 generation caps in the suite definition; 4 suite size and language mix; 5 item provenance and contamination-risk marking; 6 runtime repetition, median, N, mean and standard deviation with the raw repetitions retrievable; 7 machine state at start and the unreliable flag on excess spread; 8 the reproduction verdict for both quality and runtime; 9 failed-generation scoring and reason, never silently dropped; 13 the versioned roster file every row's fiche cites; 14 fiche integrity by SHA-256 with invalidation of the rows referencing an edited fiche; 15 energy, emissions, factor, region, method, and the cloud Scope-3 estimate with its formula id; 16 cost, cloud tokens and list price, local kWh price; 19 run provenance including release version and commit sha.
- Includes: making the hardcoded server flags, model file and llama.cpp build roster- and settings-driven rather than constants, because criteria 13 and 14 cannot be satisfied while a row's fiche is an assertion in source.
- Includes: republishing **the reference bundle**, not only the two JSONL files. A row cites its fiche, roster entry, suite definition and prompt template by hash or id, so the row alone verifies nothing; what is published is `aidd_docs/results/{runtime,quality}-reference.jsonl` plus the fiche registry, the roster file, the suite definitions and the prompt templates the rows point at. The current reference files are retained as superseded, renamed and marked with the schema version that produced them, rather than deleted — the repo keeps published evidence for the epic's duration.
- Includes: the **classification suite's compliance with criteria 4 and 5**, in two separable pieces. First, the rule, the gate and the tags: per-item language tag, per-item provenance and contamination-risk marking on the ten items that exist, and the indicative marking a below-threshold suite receives. This is what the sibling epics wait on and it is provable by deliberately shrinking a suite, without twenty items existing. Second, the **one-time retrofit from 10 items to 20** under the EN/FR/DE ≥25% mix, natively authored rather than machine-translated from the EN ten, and carrying the regeneration of the reproduced-twice quality evidence its suite-version bump retires. This is the only suite that exists, so it is the only suite this epic touches.
- Excludes: authoring or scoring any new task suite. The translation and rewriting suites belong to `quality-scored-comparison-first-three-use-cases`; their stories cite criteria 4 and 5 as acceptance and are born compliant against the gate this epic ships — they do not re-implement it.
- Excludes: the **suite definition shape and its registry**, which `no-use-case-is-silently-absent` claims and which six suites, not one, are what justify them. This epic ships the gate and puts the criteria 3, 4 and 5 fields on the one suite that exists, in whatever form that module already takes; the shape those fields become, and the registry that resolves a suite id to a definition, arrive with the second suite. The gate validates fields, not a shape, so it survives the generalisation unchanged.
- Excludes: criteria 10 and 11, the judge protocol and judge independence. They arrive with the second cloud provider and the judge machinery, in their own epic. This epic leaves the row schema open for the fields they add.
- Excludes: criteria 17 and 18, web-research archival and suite shape, which belong to `aidd_docs/backlog/epics/no-use-case-is-silently-absent.md`.
- Excludes: the surface that shows these fields to a decision-maker. The results service and dashboard are a separate epic; this epic makes the data exist and be correct, not readable at a glance.
- Excludes: CI, container packaging and release tagging as such — with one seam: criterion 19 needs a release version to record, so this epic records whatever version identifier exists and does not invent the tagging process.
- Excludes: revising the Methodology's thresholds. 20 items, N≥5, 10%, 25% per language are taken as the PRD's stated initial values and implemented as configured constants, not re-derived.

### Decisions this epic takes

Four criteria state an observable outcome — a flag, a verdict, an invalidation, a method label — without naming the quantity or the observation that produces it. A test author cannot write the test from the PRD's text, so the epic decides them here rather than letting each story pick one. Each decision that widens a criterion beyond the PRD's wording is marked `→ PRD`; the PRD is the place they are finally recorded, not this file.

| Criterion | Decision taken here |
| --- | --- |
| 1 runtime half | A runtime row either pins a seed — departing from the frozen baseline command and requiring its re-validation — or records the absence of one as a named source of the spread criterion 7 measures. Recording sampling values that did not determine the output is not enough. |
| 2 | Scoped to recording the endpoint, the template id and the template content hash, with `none` a legitimate template value for the raw completion path. Shippable now, correct after the chat-endpoint migration, and what makes rows on either side of it distinguishable. |
| 6 | Names the metric set it aggregates. Memory figures (VRAM, RSS) are published as peaks over the repetition, never as point samples — sizing is the question a client engineer asks first and a sample cannot answer it. Every non-timing measurement on an aggregated row declares its aggregation (which repetition, or which statistic), the same discipline the timing fields already carry. → PRD |
| 6 + 9 | A failed repetition does not silently vanish: the row states the rule (dropped and re-run, kept, or the whole row failed) and the failure taxonomy distinguishes truncation at the row's `max_tokens` cap from truncation at the context limit — criterion 3 makes the cap a suite-level choice a challenger can dispute. → PRD |
| 6 protocol | The repetition protocol is row data, not convention: warm-up count discarded, whether the server process restarts between repetitions, repetition index, and the named location of the raw repetitions. A re-run matches the protocol instead of guessing it. |
| 7 | The spread statistic and its denominator are named in the implementation and stated with the flag rate they imply on the validated baseline, so the first full-roster run can falsify the choice. The threshold stays 10%; which statistic 10% is *of* decides whether the flag never fires or always fires. → PRD |
| 8 | One primary metric carries the verdict; the others are reported as deltas. A verdict computed on an unnamed "median" is untestable, and TTFT is far more volatile than throughput. → PRD |
| 8 | A third state, `not comparable`, naming the fiche fields that differ. Driver and build drift without anyone touching the benchmark, and the client engineer reproducing on their own machine is the epic's stated audience — two states hand them a false `not reproduced`. The epic also states which fiche fields are verdict-blocking (build, quant, flags, GPU) and which are recorded only. → PRD |
| 8 reference | The row records the run id of the reference it was compared against. The reference files are curated snapshots no CLI writes to (`aidd_docs/results/README.md`), and the surface epic computes nothing at read time, so the verdict is produced and stored by the harness against a named reference. |
| 13 | The roster entry carries the model architecture (dense or MoE, with expert count), without which Methodology 13's "a dense model takes no MoE-offload flags" rule has nothing to check against and `--n-cpu-moe`'s ceiling has no bound to validate. Its first entry reproduces the validated baseline flag set byte for byte, so the republished rows stay comparable to the two that carry the project's headline throughput. The per-request sampler override in the quality path stays the single source of quality sampling once flags are roster-driven. → PRD |
| 14 | The hash is computed over a normalised projection of the fiche: the model identified by roster entry id and checksum rather than by its filesystem path, host and port excluded. Today's flag list opens with an absolute `D:\ia\models\...` path, so the hash changes when `SLM_MODELS_DIR` moves and no second machine can ever match it. The raw flag list stays on the row as evidence. → PRD |
| 14 | Invalidation is observable as a named validator command with a non-zero exit, the only form that survives this epic's exclusion of the results surface. The fiche is a stored addressable artifact, not a reconstruction from a row. |
| 15 | The energy method is per channel (`cpu_energy_method`, `gpu_energy_method`) with the component values, so a composite figure is not labelled by its smaller measured half. The row also records the scope boundary behind its emissions figure — local is CodeCarbon offline Scope 2, cloud is a Scope 3 formula covering datacenter overhead and hardware amortization — and the epic states plainly that the two are not like-for-like until a local Scope-3 component exists. → PRD |
| 16 | A cloud row stores the list price value, its currency and its retrieval timestamp, not only the derived cost — mirroring how criterion 15 stores the emission factor beside `energy_kwh`. Rows also carry one normalization unit, chosen once for the project, so an on-prem cost and a cloud cost are comparable rather than merely both in euros. Publishing a comparable unit is reporting, not optimising. → PRD |
| 19 | Run provenance records the commit sha plus a dirty-tree flag. A sha stamped from a modified working tree names code that never existed, which is the exact artifact this epic exists to remove. The version falls back to the packaged version when no release identifier exists. → PRD |
| row contract | Every row carries `schema_version`, and the epic states what happens to a live per-machine store holding pre-schema rows (rotate on change, or filter by version at read time). Without it the surface epic's declared-absent contract cannot tell a stale row from an honest degradation, and those are opposite claims. |
| beyond the 19 | `ttft_source` on every runtime row. TTFT is server-reported and uncorroborated, the code says so in a comment no published row carries, and it is the easiest of the three headline metrics for a sceptic to dismiss. Corroboration needs slot isolation and stays out of scope; publishing the number unlabelled does not. → PRD |
| 5 | Item provenance is an author declaration gated for presence and consistency, not a verified property. Nothing detects a public item declared hand-written. Stated so the limit is disclosed rather than discovered. |

## Success Evidence

Take one published row from the regenerated reference files, hand it to someone who did not produce it together with the published reference bundle it cites — fiche registry, roster file, suite definitions, prompt templates — and give them nothing else. They can name the exact model and roster entry, the exact prompt as sent and the path that sent it, the caps, the sampling values, the machine it ran on by fiche hash, the code sha and whether the tree was clean, and how much of its energy figure was measured rather than estimated. They then re-run it and receive a verdict — reproduced, not reproduced, or not comparable with the differing fields named — rather than two numbers to compare by eye.

The row alone is deliberately not sufficient: criteria 13 and 14 replace today's inline flattening with pointers precisely so a row can be invalidated when what it points at changes. The bundle, not the line, is the unit an auditor is handed.

Six checks confirm or challenge it, each able to fail. The first four are code-level, run on constructed rows and stubs, and are cheap enough to run on every change; the last two need the bench machine and a quiet thermal window.

- A row missing any required field of the row contract cannot be written: the writer gate refuses it. This is what makes the schema-shaped criteria (2, 3, 5, 9, 13, 15, 16, 19) able to fail rather than merely able to be described.
- A runtime row published without N, median, mean, standard deviation and its raw repetitions cannot be produced by the harness at all.
- Editing a hardware fiche invalidates the rows citing its hash, demonstrably: a named validator command exits non-zero and names the rows.
- The verdict logic, exercised against constructed reference and re-run rows, returns "reproduced", "not reproduced" and "not comparable" in the three cases that produce them, and returns "not comparable" — not a false failure — when the fiche's verdict-blocking fields differ.
- A suite of fewer than 20 items, or one whose EN/FR/DE mix falls below 25%, publishes its score marked indicative — verified by deliberately shrinking a suite.
- Two real runs on the bench machine produce a verdict with the thermal and load hints of both runs attached, and the 10% tolerance is recorded against the observed spread rather than assumed to fit it. This check calibrates the threshold; it does not gate the verdict logic, which the constructed-row check already covers.

Once `done`, record here what a real client engineer's audit of a row actually surfaced, and whether any of the four thresholds moved on contact with the first full-roster run.

## Dependencies and Unknowns

| Item | Kind | Handling |
| --- | --- | --- |
| Which thermal and load signals actually explain observed runtime variance on this platform, at the project's privilege level (criterion 7) | spike | Frame a spike before the criterion 7 work. Its premise is now measured rather than assumed: `psutil.sensors_temperatures` does not exist on Windows at all (`hasattr` is `False` on psutil 7.2.2, so it raises rather than returning an empty mapping), and `psutil.getloadavg()` is a Windows emulation that returned `(0.0, 0.0, 0.0)` while `cpu_percent(interval=1)` read 2-3% — a fabricated zero is exactly the unfalsifiable number this epic removes, so load *cannot* be the fallback hint. The expected answer is the NVML path the repo already owns: GPU temperature and clock event reasons, both readable at ordinary privilege. CPU package temperature degrades to a declared-unavailable state with the same honesty discipline as `energy_method`. |
| The repetition topology for criterion 6, and the inter-repetition thermal posture | decision | Taken during delivery, before the criterion 6 story. Both obvious choices are already documented as wrong in the code: repetitions inside one server process make repetition 1 systematically slower (the warm-up that would fix it "bled its context into the measured request via the shared `-np 1` slot and wrecked `gen_tok_per_s` (26 -> 11.8)", `__init__.py:29-40`), while one process per repetition pays a ~15 GB model load each time under `--load-mode none`. The discarded-first-repetition option — run N+1, discard the cold one, record that the discard happened — is stated explicitly as a candidate. Measuring model load time once is the cheap prerequisite that turns the wall-clock estimate below into a number. The posture (back-to-back, fixed cooldown, or cooldown to a GPU temperature ceiling) is declared on the row, because it decides whether a published row describes a cold machine or a saturated one and both are defensible only when declared. |
| N≥5 repetitions multiplies every runtime measurement's wall-clock by ~5 on the single development machine | assumption | Accepted: repetition count is configurable with 5 as the default, so a development loop can lower it while a published row cannot. Note that the multiplication is not only cost: this machine's only sustained-session evidence is a 34% swing attributable to GPU thermals (`gen_tok_per_s` 26.0 and 25.5 on the curated rows against 17-18 on same-day rows measured in `sw_thermal_slowdown`, `aidd_docs/results/README.md`), against ~3.9% across the three rows measured at the final prompt length. Five back-to-back repetitions change the thermal regime the measurement is taken in, so criterion 7's flag firing on a laptop is the honest outcome, not a threshold to tune away. |
| Whether EN/FR/DE is a coverage rule or a reported dimension (criterion 4) | decision | Not taken here; it is a PRD criterion question. Twenty items at ≥25% leaves five per minority language across four labels, so a per-language accuracy moves in 20-point steps and "German 60%" from five items is the class of number this epic exists to prevent. This epic implements the tag and the suite-level gate either way; whether a language cell is *scored*, and whether a below-threshold cell is marked indicative under the same rule criterion 4 applies to a whole suite, is recorded for the PRD. |
| The normalization unit behind criterion 16, and the scope-boundary asymmetry behind criterion 15 | decision | Both recorded for the PRD rather than chosen here. The epic ships the fields (unit per row, scope boundary per row); which unit, and whether a local Scope-3 component is ever added, are criterion changes. |
| The tracked reference rows predate the schema and cannot be retro-tagged with a fiche hash, roster entry or commit sha they never carried | assumption | Accepted: they are regenerated, not migrated. The old rows are retained as superseded and marked with the schema version that produced them, rather than reinterpreted or deleted. |
| The untracked live per-machine stores are not regenerated, and already hold three row shapes in ten rows on this machine | decision | `schema_version` on the row contract plus a stated rule — rotate the store on a schema change, or filter by version at read time. Either is fine; silence is not, because the surface epic's declared-absent contract already depends on telling "absent because the row predates the field" from "absent because the value was genuinely unavailable", and those are opposite claims. |
| The Methodology thresholds (20 items, N≥5, 10%, 25%, 80%) are initial values the PRD itself flags as possibly needing to move after the first full-roster run | decision | Deferred to that run, per the PRD's own Open Questions. The gate, not this epic's authorship, is what makes them compliant. |

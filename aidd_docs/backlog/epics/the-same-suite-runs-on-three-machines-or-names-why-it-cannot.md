# Epic: The same suite runs on three machines, or names why it cannot

Given the repository cloned onto the tower, the laptop and the no-GPU professional PC, the same suites produce rows that merge into one published bundle in which every number names the machine and the compute mode that produced it — and a model that does not fit a machine in a mode refuses the run naming the requirement it failed, rather than being quietly missing from the table.

## Context and Value

The audience is the one the PRD names as thinnest-served and the publication's differentiator: "Published evidence about small language models on ordinary hardware is thinnest exactly where a professional buyer needs it: a 16 GB office PC with no GPU is nearly absent from the literature, so a machine that cannot run a model at all and one that runs it acceptably are indistinguishable to anyone reading current results" (PRD, Problem Statement). The PRD already carries the criteria — Methodology 21 (machine dimension, compute mode and run profiles), Methodology 8's rule that a `gpu` row and a `cpu_only` row are not comparable, Methodology 14's fiche carrying the compute mode, and acceptance criteria 121, 122 and 123. None of them has any implementation behind it.

Verified current state, at `0f849c8`:

- **Compute mode does not exist in the code.** `grep -rn "compute_mode\|cpu_only" src/` returns nothing outside compiled caches; the only related hits are three `n_gpu_layers` references (`roster.py:45,325`, `server.py:77`). There is no mode on any fiche, any row, any roster entry or any setting.
- **The fiche hash cannot distinguish the two modes on one machine, and the consequence is a silently wrong fiche.** `_NORMALISED_KEYS` (`src/wave_local_ai_v2/hardware.py:44-55`) is `cpu, ram_gb, gpu_name, gpu_driver_version, os, cuda_ceiling, llama_cpp_build, quant, roster_entry_id, model_sha256` — `flags` is excluded by design, and the comment says so. `-ngl 99` and `-ngl 0` therefore hash identically, and `gpu_name`, `gpu_driver_version` and `cuda_ceiling` come from an NVML capture (`hardware.py:126-136`) that runs whether or not the GPU is used. Two runs of one model on the laptop, one `gpu` and one `cpu_only`, produce **the same `fiche_hash`**. Trace what follows: `fiche_registry.write_fiche` is write-once by hash and "if `registry_dir/<hash>.json` already exists, does nothing" (`fiche_registry.py:30-45`), so the `cpu_only` run's own fiche is never stored and the `gpu` fiche stands in for it — a published fiche whose `flags` say `-ngl 99` for a run executed entirely on the CPU. `verify_fiche` reports `ok`, because the stored file still hashes to its own name. And the verdict, which selects a reference on `_RUNTIME_BLOCKING_FIELDS = ("llama_cpp_build", "quant", "gpu_name", "flags")` (`verdict.py:24`) resolved *from the registry by the row's hash* (`verdict.py:43-47`), reads the same stored flags for both rows, finds all four fields equal, and returns a throughput `reproduced` / `not_reproduced` verdict between a GPU run and a CPU run. That is precisely what Methodology 8 forbids — "a `gpu` row and a `cpu_only` row from the same machine are not comparable and must never be read as a failed reproduction of each other" — and the `flags` field that would otherwise have caught it is defeated by the collision upstream of it. This is the single field that has to move for the epic's outcome to be reachable at all.
- **The host seam is exactly one machine wide.** Each roster entry carries a `validated_host` block holding one `n_cpu_moe`, one `threads` and a free-text `fiche_summary` — "Consumer NVIDIA laptop GPU, ~6 GB VRAM, Windows", repeated verbatim on all four entries (`aidd_docs/roster/models.json`). The overrides are process-global: `SERVER_N_CPU_MOE` and `SERVER_THREADS` (`settings.py`, `host_n_cpu_moe` and `host_threads`) apply to whichever entry the run selects, so a second machine's settings can only be expressed by editing `.env` per run. There is no key by which a value could be per (model x machine), and the machine itself is a sentence, not an identifier.
- **`-ngl` sits on the wrong side of the model-intrinsic / host-fitted split.** `n_gpu_layers` is roster data inside `server_flags` and is emitted from the entry by `server.build_flags` (`server.py:74-78`). A `cpu_only` profile needs `-ngl 0`, which is a per-(model x machine x mode) override of a field the current design treats as a property of the model. In the same launch, `--n-cpu-moe` becomes meaningless when every layer is already on the CPU, and `roster.validate_host_fit` (`roster.py:288-310`) has no notion of mode: it checks dense-versus-MoE and the expert-count ceiling and would accept `--n-cpu-moe 37` alongside `-ngl 0`.
- **No model declares a minimum, and nothing refuses.** No roster entry carries a RAM, VRAM or disk requirement. The requirements exist only as README prose for a human — "32 GB system RAM", "~18 GB free disk" for the flagship (`README.md:39-46`) — which no code reads. AC 121's refusal has nothing to refuse against.
- **The memory difference the publication wants to measure has no field to live in.** The fiche records `ram_gb: 31.4` and nothing about memory type or rated speed. Both 32 GB machines will report ~31.4. Their hashes will still differ (their `cpu` strings differ: `platform.processor()` on the laptop returns `AMD64 Family 25 Model 80 Stepping 0, AuthenticAMD`, a family/model/stepping string rather than a marketing name), but no reader of the bundle can tell which row ran on DDR4-3200 and which on DDR5-6000. The project's own baseline prompt, published inside `runtime-reference.jsonl`, asks a fiche to carry "RAM size **and speed**"; the code captures only size.
- **The machine set is two machines, in French, outside the repo.** `context_input/hardware.md` is 20 lines describing the laptop and the tower — no professional PC — and is source material, not a published artifact. README's "Hardware you need before downloading anything" (`README.md:35-62`) describes one machine's class and closes with "not a guarantee for every machine". The one target the publication most needs is the one nothing in the repo describes.
- **Rows from a second machine have no path in.** The live stores are per-machine and gitignored (`.gitignore:25-27`); the two `*-reference.jsonl` files are "curated snapshots: no CLI ever writes to them" (`aidd_docs/results/README.md`). Three machines writing `runtime.jsonl` produce three files of the same name and no defined merge. The committed bundle is a single machine's evidence by construction.

The value is that without this epic the publication's headline claims are one laptop's numbers. The no-GPU professional PC is the case the PRD says the literature omits and the reason a professional buyer would read the paper at all; running the two 32 GB machines `cpu_only` is the only way their memory difference becomes a measured comparison instead of a confound buried in two incomparable GPU rows. And the refusal is half the result: a reader learns as much from "this model will not run on your office PC, for want of 9 GB of RAM" as from a throughput figure, but only if the absence is named. A blank cell in a published table is not evidence.

## Boundaries

- Includes: a **declared machine registry** — one tracked entry per target machine with a stable machine id, the host-fitted values that are genuinely per-machine, and the fields the fiche cannot capture (memory type and rated speed, allocatable VRAM where it differs from nominal, whether a GPU is present at all). The three PRD machines are its first three entries, translated from `context_input/hardware.md` and extended with the professional PC that file omits.
- Includes: a **run profile registry keyed by (roster entry x machine x compute mode)**, holding the flag overrides that triple owns — `-ngl 0` and no `--n-cpu-moe` under `cpu_only`, the per-machine `--n-cpu-moe` and thread count under `gpu` — resolved through the existing `server.build_flags` rather than a second flag builder. `validated_host` collapses into it; two places to read a thread count from is one too many.
- Includes: **declared minimal requirements per roster entry per mode** (RAM, VRAM, disk) and the pre-flight check that refuses a run naming the requirement, the mode and the observed value, exits non-zero and writes no runtime row. No substitution of a smaller quant, a shorter context or a CPU path on the harness's own initiative.
- Includes: **compute mode and machine id on the fiche and inside its hashed projection**, and on every row — with the republication of the reference bundle that a change to `_NORMALISED_KEYS` forces, under the row epic's established supersede-don't-backfill discipline.
- Includes: a **`cpu_only` row's VRAM figure declared not applicable**, never zero, per Methodology 21. The GPU fields stay on the fiche of a `cpu_only` run on a GPU-bearing machine: erasing them would hide that the memory comparison ran on machines that have GPUs and chose not to use them.
- Includes: the **operational path across N machines** — what a machine pulls from a fresh clone, and how its rows come back. Decided here: a per-machine tracked results file, one branch and one pull request per machine through the check suite `clean-machine-runs-it-and-nothing-reaches-main-unchecked` already ships, and a merge step that assembles one bundle keyed by fiche hash and **refuses a collision** (two rows sharing a fiche hash under different machine ids) rather than choosing between them.
- Includes: the **professional PC's own setup path in the README** — a no-GPU, 16 GB target is the one configuration the current hardware section does not cover, and the two new machines execute that epic's fresh-machine walk for real.
- Includes: **the DDR4-versus-DDR5 `cpu_only` pair and the no-GPU PC's rows as ordinary published rows**, distinguished by machine, never marked degraded (AC 122, 123).
- Includes: **a published record of every refusal**, so a hole in a published table carries its reason. A refusal is not a runtime row and never becomes one; it is a separate, tracked statement that this (model x machine x mode) was declared, attempted and refused, with the requirement named.
- Excludes: **new models, families or quants.** Roster composition (the gap brief's gap 2) is its own epic. This epic adds requirement and profile fields to the four entries that exist and stays correct as the roster grows.
- Excludes: **new suites, inference engines, agentic harnesses, prompt variants and inferential statistics** (gaps 3, 4, 5, 7). Each is a further row dimension and none of them is this one.
- Excludes: **the judge machinery and any judged score.** Quality is machine-independent; judge calls do not multiply per machine, and this epic adds no judged row.
- Excludes: **rendering the machine dimension to a decision-maker.** `the-pitch-runs-from-a-browser-and-only-with-the-key` owns the four views; this epic makes machine and mode exist and be correct on the row, not readable at a glance. The seam is that its runtime view already names fiche fields and gains two.
- Excludes: **the fiche's hashing mechanism, its write-once registry and its invalidation validator.** Criterion 14 is the row epic's and is shipped; this epic adds two fields to the projection that mechanism hashes and inherits the regeneration that follows, without rebuilding the mechanism or re-litigating what else belongs in the projection.
- Excludes: **the row contract, the writer gate and the verdict logic themselves.** `every-published-row-explains-and-reproduces-itself` owns them. This epic adds two fields to the contract and one consequence to the verdict — compute mode is verdict-blocking, and a mode mismatch returns `not_comparable` naming it — and rebuilds neither.
- Excludes: **CI, branch protection and the container image as such.** The clean-machine epic owns them; this epic passes its per-machine result files through the gate that epic already provides.
- Excludes: **a direct memory-bandwidth microbenchmark.** The comparison is made by running the same suites under the same profile shape, not by a synthetic probe.
- Excludes: **re-deriving the PRD's thresholds** (N>=5, 10%, 20 items). Taken as given; a `cpu_only` profile is slower, not differently governed.

### Decisions this epic takes

| Subject | Decision taken here |
| --- | --- |
| Fiche identity | `compute_mode` and `machine_id` enter `_NORMALISED_KEYS`. Compute mode must, or a `gpu` and a `cpu_only` row from one machine are the same identity and Methodology 8's rule cannot be enforced. Machine id enters too rather than trusting `cpu` plus `ram_gb` to separate machines: `platform.processor()` yields a family/model/stepping string, so two machines of one CPU generation and one RAM size would collide silently, and the failure mode of that collision is a false `not_reproduced` between two different computers. → PRD |
| Memory type and speed | Attributes of the **declared machine entry**, not new hashed fiche fields — the machine id already carries them into the hash by reference. Declared rather than captured: WMI can read `SMBIOSMemoryType` and `ConfiguredClockSpeed` on Windows but not on every platform this may run on, and a field that degrades to `None` on one machine is the fabricated-absence problem the row epic exists to remove. The declaration is marked as declared, with the same honesty discipline as `energy_method`. |
| `-ngl` ownership | The profile overrides `server_flags.n_gpu_layers`; the roster keeps the model-intrinsic default. One resolution order — entry default, then profile override, then explicit operator override — and `server.build_flags` stays the single flag builder. |
| `--n-cpu-moe` under `cpu_only` | Absent, not zero. `--n-cpu-moe 0` instructs llama.cpp to offload *no* experts to the CPU, the opposite of what `cpu_only` means, so the two are not interchangeable. `validate_host_fit` gains the mode and refuses a value supplied under `cpu_only` rather than dropping it silently. |
| Requirements are declared, not verified | Per entry, per mode, author-declared and checked against what the machine reports. Nothing verifies that a declaration is *right*; a too-low declaration surfaces as a run that starts and then fails. Stated so the limit is disclosed rather than discovered. The first declarations are calibrated from peaks the existing rows already publish (15.2 GB RSS for the flagship, 1.1 GB for the 0.6B, `README.md:48-52`), not invented. |
| A refusal is published | AC 121 says the run refuses and no row is produced; the epic's outcome says the absence must be named. Both hold: the refusal produces no runtime row, and the campaign's declared profile set plus a refusal record make the resulting hole readable. A blank cell with no record is the failure this epic exists to prevent. → PRD |
| Row transport | One tracked results file per machine, one branch and one pull request per machine, merged into a bundle keyed by fiche hash. Every published number then arrives through a check that could have refused it — the same standard the branch-protection epic sets for code. Where a machine cannot push (see Dependencies), the documented fallback is an operator-carried file committed from a machine that can, recorded as such rather than passed off as the machine's own push. |
| Machine identity across changes | A machine entry describes a declared **configuration**, not a physical box: a RAM upgrade or a GPU swap is a new entry with a new id, mirroring how the fiche already treats a driver version change. |
| The DDR4/DDR5 comparison is published as machine-versus-machine | The two 32 GB machines differ in more than their memory: 6 Zen4 cores against 8 Zen3 cores, different IPC, and different instruction-set support (`context_input/hardware.md` records "pas d'AVX-512" on the 5800H). `cpu_only` removes the GPU as a variable; it does not isolate memory bandwidth. The result is published as one machine against another with the memory generation as the headline difference **and the CPU difference stated beside it** — never as a clean DDR4-versus-DDR5 measurement. Publishing it as the latter is the class of overclaim a reviewer removes first. → PRD |

## Success Evidence

The proving pass, done for real: one roster model, three machines, every mode applicable to each, each from a fresh clone following the README alone — then the three pull requests merged into one bundle. The full roster x machine x mode campaign is publication production run *against* this machinery and is not this epic's done gate; what closes the epic is that the path works end to end on every machine, including the one with no GPU.

Seven checks, each able to fail. The first four are code-level and run on constructed fiches, rows and stubs; the last three need the machines.

- Two runs of one model on one GPU-bearing machine, one `gpu` and one `cpu_only`, produce **two different `fiche_hash` values**, two separately stored fiches each carrying its own flag list, and a `not_comparable` verdict between them naming `compute_mode` — not a throughput verdict. Run today, this check fails at every step: the hashes are equal, the second fiche is never written, and the verdict compares the two runs against one stored flag list.
- A profile whose declared minimum is deliberately raised above the machine refuses, and lowered below it runs — so what the check tests is the declaration, not the machine that happens to be under it.
- A `cpu_only` row carries an explicit not-applicable VRAM figure, and no zero appears anywhere a VRAM value would be read.
- A merge of two machines' result files whose rows claim one fiche hash under different machine ids is refused, naming both.
- On the 16 GB no-GPU professional PC, the flagship refuses before `llama-server` starts, names the RAM requirement and the mode, exits non-zero and writes no row; a model that does fit produces an ordinary published row on the same machine in the same session.
- The merged bundle, assembled from three machines' pull requests, resolves every pointer (the assertion `tests/test_reference_bundle.py` already makes), every row's machine id resolves to a declared machine entry, and no two machines' rows share a fiche hash.
- Handed the merged bundle and nothing else — no access to `context_input/hardware.md`, which is French, untracked as a published artifact and lists two machines — a reader can name, for any row, which machine and which compute mode produced it, and which memory generation that machine has.

Once `done`, record here what the professional PC actually needed that the README did not say, which (model x machine x mode) combinations refused and on which requirement, and how the observed `cpu_only` throughput gap between the two 32 GB machines compares to the ~2.4x memory-bandwidth ratio the source notes assert — including whether the CPU-generation confound turned out to be the larger term.

## Dependencies and Unknowns

| Item | Kind | Handling |
| --- | --- | --- |
| The professional PC may be corporate-managed: installing `llama-server`, downloading multi-GB weights and pushing to GitHub can all be policy-blocked | dependency | The most consequential unknown in the epic, since that machine is the publication's differentiator. Resolve it before the profile work, not during the proving pass: confirm install rights, disk headroom and git push credentials on that machine first. The transport decision assumes push rights; the operator-carried fallback in the decisions table exists for exactly this case and is documented rather than improvised. |
| Adding two keys to `_NORMALISED_KEYS` changes every existing fiche hash, invalidating the 5 committed fiches and the 82 rows citing them | dependency | Accepted, and handled by the row epic's existing rule: regenerate, retain the superseded files marked with the schema version that produced them, never back-fill. `aidd_docs/results/README.md` already records a pending schema-8 regeneration filed in `backlog/tech-debt.md`; fold the two into one bench session rather than paying the quiet-thermal-window cost twice. |
| Whether `-ngl 0` behaves with `-fa on` and `--load-mode none`, which are validated only in the GPU configuration | spike | Cheap and early: one launch per machine before any profile is authored. The flag set was tuned against a GPU path and the interaction is unverified, not assumed broken. |
| `cpu_only` wall-clock, and the N>=5 repetition multiplier on top of it | assumption | Accepted, and bounded by scope rather than by tuning: the machinery must support `cpu_only` for any profile; the *campaign* chooses which models actually run in it. The flagship already runs 37 of its 40 expert layers on CPU at ~25 tok/s, so a full-CPU run of it is the expensive end and is a campaign decision, not a gate on this epic. |
| Whether the 16 GB professional PC holds any of the four current entries `cpu_only` alongside Windows | unknown | Answered by calibrating the requirement declarations against measured peaks, then observed on the machine. If nothing in the current roster fits, the outcome is a machine with three named refusals and no rows — a publishable result, and exactly what "not a silent absence" means. The gap brief's Granite 350M sits in the roster-composition epic, not here. |
| Roster growth multiplies profiles: 3 machines x 2 modes x every future model | assumption | Profiles resolve from per-(machine, mode) defaults and are overridden only where a model needs it, so adding a roster entry does not mean hand-writing six profiles. If that resolution turns out to need per-model values everywhere, the registry's shape is wrong and this is where it shows. |
| The two 32 GB machines differ in CPU generation as well as memory generation | decision | Taken above: published as machine-versus-machine with the confound stated. Recorded here as an unknown too, because which term dominates is not knowable before the runs and it decides how the result can be claimed. |
| Continued availability of all three machines | dependency | Named in the PRD's Dependencies: "a missing machine leaves a hole in every comparison that cites it". The gap brief confirms all three are available now. |
| `context_input/hardware.md` is French source material and the repo's language rule is English-only for artifacts | decision | The declared machine registry is the English artifact; the French notes stay source material and are not committed as a published fiche. The professional PC's fields do not exist there at all and are captured fresh. |
| The PRD and the code disagree on how a reproduction reference is selected | decision | Methodology 8 says a reference must share "the re-run's normalised fiche hash"; `verdict.select_runtime_reference` instead matches four blocking fields (`llama_cpp_build`, `quant`, `gpu_name`, `flags`), which is stricter on flags and looser on CPU, RAM, OS and driver. Not resolved here — it is the row epic's criterion — but named, because this epic adds `compute_mode` to the blocking set and would otherwise add it to whichever of the two definitions a story happened to read. Add it to both, and record the divergence for the PRD. → PRD |
| Whether the campaign runs judges once or per machine | assumption | Once. Quality is machine-independent, so a judged score is not re-earned per machine and the gap brief's ~$10 judge budget does not multiply by three. Stated because the opposite assumption would triple a paid budget silently. |

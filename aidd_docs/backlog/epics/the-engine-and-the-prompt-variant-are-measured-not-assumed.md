# Epic: The engine and the prompt variant are measured, not assumed

Given any published row, a reader sees which inference engine produced it and which prompt variant it ran under — both declared before the campaign rather than chosen at the call site — and the benchmark states, per task family and with a paired test behind it, whether each variant helps or hurts a small model on quality, TTFT, tokens and energy.

## Context and Value

The audience is the consultant the PRD's user story names — "As a consultant, I want the inference engine, the agentic harness and the prompt variant compared as dimensions, so that I can recommend a whole stack for a use case rather than only a model" — and the academic reviewer the publication adds, for whom an unnamed engine is an unnamed confound. The PRD carries the substance of this epic as Methodology 22 and as one of its Open Questions: "Whether prompt compression helps or hurts a small model, in quality and in TTFT, and whether the answer differs for agentic work — the benchmark's own open research question."

This epic also reopens a founding decision, deliberately and without reversing it. `aidd_docs/memory/architecture.md` records **llama.cpp over Ollama** under Key decisions: "direct control over inference flags (`--n-cpu-moe`, `-fa`, `--jinja`, etc.), quantization choice, and memory layout; Ollama abstracts these away." That reasoning is sound as a build decision and it is not in dispute here. What it lacks is a number. The decision was taken to make the benchmark controllable, not because Ollama had been measured and lost; this epic produces the measurement the decision was taken without. If llama.cpp wins, the founding decision becomes evidenced rather than asserted, which is worth more to a reviewer than the assertion. If Ollama wins on some axis, the write-up says so.

Verified current state, at `0f849c8`:

- **There is one engine and it is a module constant.** `server.py` pins `HOST = "127.0.0.1"` and `PORT = 8080` (`server.py:28-29`), `build_flags` emits llama.cpp's own flag spellings (`-ngl`, `--n-cpu-moe`, `-fa`, `--jinja`, `--load-mode`, the sampler flags), and `start_server` refuses to launch when the port already accepts connections (`server.py:155`) — a guard that is exactly right for a process this harness spawns and exactly wrong for a daemon that is already running, which is the normal resting state of the second engine.
- **The fiche's hashed identity names one engine.** `llama_cpp_build` is a field of `Fiche` (`hardware.py:32`) and a member of `_NORMALISED_KEYS`, the projection `fiche_hash` is computed over (`hardware.py:45-56`). A row produced by another engine has no llama.cpp build; leaving the field null would place an absence inside an identity, and no field says which engine the build belongs to.
- **Nothing on a row names an engine or a variant.** `row_contract.py` is at `SCHEMA_VERSION = "11"` (`row_contract.py:69`) and neither string appears anywhere in it. Both dimensions are absent as data, so every runtime and quality number the repo has published is a llama.cpp, baseline-prompt number that does not say so in a form a reader can select on.
- **The rendered prompt comes from one server's own endpoint.** `local_client.render_prompt` posts to `/apply-template` and the row records `prompt_capture: reconstructed` (`prompt_provenance.PROMPT_CAPTURE_RECONSTRUCTED`), with `prompt_template_id` fixed at `llamacpp-model-chat-template` and the per-row hash taken over the Jinja source read from `/props`. Methodology 2 requires "the final prompt string as rendered for that provider". There is no second engine's equivalent in the code, and whether the second engine exposes one at all is unverified.
- **The one thinking switch is a Qwen template convention, hardcoded.** `local_client._thinking_kwargs` maps `thinking_policy: disabled` to exactly `{"chat_template_kwargs": {"enable_thinking": False}}` (`local_client.py:74-75`). The roster epic already flagged this as per-model; it is also per-engine, because a second engine either forwards that kwarg to the template, spells the control as its own request parameter, or offers none — and a row still publishing `thinking_policy: "disabled"` in the third case is the unfalsifiable row the row epic exists to remove.
- **There is no variant machinery of any kind.** A suite item's prompt reaches the model as authored. There is no grammar, no compressor, no transformation record; `prompt_template_id` names the model's own chat template, not any transformation applied before it. The DSL and Caveman techniques in `context_input/publication_ambitions.md` have no representation in the repository, and neither does LLMLingua-2.

The value has three parts.

First, the research question is the one part of this benchmark that is research rather than measurement. The single outside figure in hand — roughly 8.5% token saving with no measured quality loss, on a coding agent — describes a frontier model in an agentic loop. It says nothing about a 0.6B model classifying a support ticket, and the direction is not obviously the same: a terse-output instruction spends instruction tokens to save output tokens, which is a losing trade on a task whose output was already two tokens, and an input compressor that drops function words may cost a small model more comprehension than it costs a large one. A benchmark that runs one prompt shape cannot answer this, and no one else appears to have answered it for models this size.

Second, the recommendation. A client asks which stack to deploy, not which model to download. The engine is half of that stack for local inference and the prompt shape is a free lever that costs nothing to pull; today the consultant can defend neither with a number.

Third, the confound. Until the engine is a row dimension, every published number silently assumes one, and a reviewer's fair objection — "these are llama.cpp numbers, would Ollama differ" — has no answer in the repository at all.

## Boundaries

- Includes: **an engine registry, one tracked entry per engine**, carrying its stable `engine_id`, how its build or version identifier is read at run time (a live probe, never a constant, in the discipline `build_probe.py` already applies to llama.cpp), the endpoint set it uses — chat, health, prompt rendering or the recorded absence of one — its process lifecycle, its default port, and its configuration defaults with, for each, how that default was obtained: declared by this project, or reported by the engine itself. An entry missing any of these does not enter a campaign, because Methodology 22 is explicit that "an engine whose defaults are unrecorded cannot be compared against one whose are."
- Includes: **two declared engines — `llama.cpp` as the reference and `ollama` as the first comparator — and the lifecycle difference between them made explicit.** `server.py` spawns and owns its process; the comparator is normally a daemon already listening, so the registry declares a lifecycle of `spawned` or `attached`, and the port guard at `server.py:155` becomes correct for both rather than being weakened for either. An attached engine is checked before the run for what it has loaded and what else it is serving, and a foreign loaded model or a second client is a refusal, not a caveat.
- Includes: **the same-artifact rule and its record on the row.** The comparator is pointed at the roster entry's own GGUF file wherever its model definition allows, and the row carries `artifact_parity`: `same_gguf`, with the loaded file's checksum matched against the roster entry's `sha256`, or `engine_supplied`, naming what the engine actually loaded and the quant it chose. A campaign cell whose two engines do not both report `same_gguf` is published as an observation, never as a paired engine comparison — the engine and the artifact would be confounded and no row could separate them.
- Includes: **the defaults side-run, on one named model, published as its own figure.** What a default Ollama install costs a user — its own quant choice, its own context default, its own template handling — is the question a consultant is actually asked, and it is not the same question as which engine is faster on one artifact. It is measured once, on one named roster model, under the full runtime protocol, and published as a distinct "what the defaults cost" figure. It is never a campaign cell, never folded into an engine comparison, and it does not consume the two-engine cap.
- Includes: **the fiche generalised from one engine to any engine.** `llama_cpp_build` becomes `engine_build` beside a new `engine_id`, both inside the hashed projection, and the engine's effective launch configuration is recorded with its own content hash over a path-free normalisation — for llama.cpp the flag list with the absolute model path replaced by the roster entry reference the row epic already established, for the comparator its model definition plus the resolved options the server reports. This inherits the reference-bundle republication that any change to `_NORMALISED_KEYS` forces, under the row epic's supersede-don't-backfill discipline.
- Includes: **the runtime protocol and the quality path both run per engine, unchanged in shape.** Warm-up excluded from N, at least 5 counted repetitions back to back, the recorded cooldown, machine state per repetition, the spread flag — all of it applies to the comparator exactly as written, and any engine behaviour that breaks it (a model unloaded during a cooldown, a request that silently reloads weights) is a property of that engine to be recorded and refused, not a reason to run it under a different protocol. A row set produced under a different protocol is not comparable and would answer nothing.
- Includes: **a prompt variant registry with four versioned entries** — `baseline`, `constrained_output`, `output_compressed`, `input_compressed` — each a declared transformation with its own id and version, versioned like a prompt template under Methodology 2, so that editing a variant's definition bumps it and every row carries which version produced it. `constrained_output` is the DSL technique's descendant, expressed as a grammar-restricted output format; `output_compressed` is the Caveman-style terse-output instruction; `input_compressed` is an LLMLingua-2-class reduction of the item's input.
- Includes: **the rendered prompt showing the transformation.** The variant is applied before the engine's own templating, and the string the row publishes under Methodology 2 is what the engine finally received, so a reader sees the variant's effect rather than a claim about it. The row carries `prompt_variant_id` and `prompt_variant_version` beside the existing template id and hash, and the writer gate refuses a row whose declared variant is `baseline` while its rendered prompt differs from the item's authored text.
- Includes: **`input_compressed` recording its compressor as a step of its own.** The compressor's id, its version and its own model identity are on the row, together with the token count before and after and the resulting ratio, and the compressor's wall-clock duration and energy are recorded as their own fields rather than folded into the generation's. TTFT stays what Methodology 20 says it is — the engine's own reported number under its `ttft_source` label — and the compressor's latency is published beside it, because adding a client-side duration to a server-reported one produces a figure that is neither.
- Includes: **the constrained variant's mechanism recorded per engine.** Grammar-constrained decoding is llama.cpp's GBNF; whether the comparator exposes the same mechanism, a JSON-schema-shaped substitute, or nothing at all is unverified and is settled by a spike before the cell is declared. The row records which mechanism was applied, so a cross-engine constrained comparison is readable as a comparison of two mechanisms where that is what it is, and the cell is dropped with its reason recorded where the comparator supports none.
- Includes: **variant applicability declared per suite, without ever changing the item set.** A variant declares which task families it applies to — compressing a fifteen-token classification item is not the technique the literature describes — and an item where the variant is a no-op is still run, records the no-op, and stays in the set. The pairing E-G's Wilcoxon needs is over identical item ids across variants; a variant that skipped items would silently change the denominator and break every paired claim this epic exists to make.
- Includes: **item scores staying per item across every variant and engine**, in the shape the quality store already holds them, so the paired tests and bootstrap intervals E-G ships apply across the new dimensions with no second statistics path.
- Includes: **the campaign declaration as data** — which engines, which variants, which roster entries, which suites, on which machine — and the check that every declared cell was actually run, so "at most 2 engines and at most 4 prompt variants" is enforced at declaration and an empty declared cell is a failure rather than a gap nobody notices.
- Includes: **the research question answered in a published, dated statement**: for each variant, per task family, whether it helped, hurt or was indistinguishable on quality, TTFT, tokens and energy, each difference carrying the paired test E-G provides or published as an observation. A finding of "no distinguishable difference" is the answer being published, not the epic failing.
- Excludes: **agentic harnesses.** `direct`, `smolagents`, `langgraph`, `pydantic-ai` and `llamaindex` are Methodology 23's dimension and belong to `aidd_docs/backlog/epics/no-use-case-is-silently-absent.md`, together with the per-call prompt overhead and the per-task metric aggregation that dimension requires. This epic adds a dimension that multiplies against that one and takes none of it.
- Excludes: **the machine dimension, compute modes and run profiles**, owned by `the-same-suite-runs-on-three-machines-or-names-why-it-cannot`. The campaign runs on one declared reference machine; the engine and variant findings are stated as single-machine claims and say so.
- Excludes: **the judge machinery, judge independence and any judged score.** A variant's effect on an open-ended suite is measured once the judges exist; this epic adds no judge and changes no judge rule.
- Excludes: **the statistics machinery itself.** Bootstrap intervals, the paired Wilcoxon, the publication suite level and the licensing rules are E-G's. This epic consumes them and produces the paired columns they operate on.
- Excludes: **the row contract's mechanism, the writer gate and the fiche hashing machinery**, owned by the row epic. This epic adds fields to the contract and to the hashed projection and inherits the republication that follows; it rebuilds neither and does not re-litigate what else belongs in the projection.
- Excludes: **roster composition.** Families, size classes and the per-entry thinking control are `every-size-class-spans-two-families-or-says-it-does-not`. This epic runs on whatever roster exists and stays correct as it grows.
- Excludes: **authoring new suites.** The campaign runs the suites that exist when it runs.
- Excludes: **a full input DSL as a fifth variant.** Re-expressing a task instruction in a compact invented syntax is the technique `context_input/publication_ambitions.md` describes from the Copilot Studio work, and it is a genuine candidate; the cap is four variants and `constrained_output` already carries the DSL idea on the output side. It is named here as a candidate for a later campaign rather than smuggled in as a fifth cell.
- Excludes: **revising the PRD's thresholds.** Two engines, four variants, N≥5 and the 10% spread rule are taken as stated initial values.
- Excludes: **rendering either dimension to a decision-maker.** `the-pitch-runs-from-a-browser-and-only-with-the-key` owns the views; this epic makes the two dimensions exist and be correct on the row.

### Decisions this epic takes

| Subject | Decision taken here |
| --- | --- |
| Campaign shape | The full cross product — 2 engines × 4 variants — runs on one declared reference machine across the roster and the suites that exist. The other machines stay reference-engine, baseline, and belong to the machine epic. Eight cells on three machines would multiply against a growing roster faster than the campaign could finish, and a finding measured on one machine and stated as such is worth more than an unfinished matrix. Every published engine or variant claim names the machine it holds for. |
| Ollama's own defaults | Measured, but never as a campaign cell. One named roster model is run under a default Ollama install and published as its own "what the defaults cost" figure. Making Ollama-as-installed one of the two declared engines would confound the engine with the artifact in every comparison; leaving it unmeasured would skip the configuration nearly every Ollama user actually runs. → PRD |
| Fiche identity | `llama_cpp_build` generalises to `engine_build`, and `engine_id` joins it inside the hashed projection. An engine is not a property of a run's flags; two engines on one machine with one model must not hash to one identity, or Methodology 8's reproduction verdict compares rows that were never comparable. → PRD |
| Engine configuration in the hash | The engine's effective configuration carries a content hash over a path-free normalisation, and that hash enters the projection. This closes for the engine dimension the same seam the raw flag list has for llama.cpp — flags stay out of the projection as evidence because they carry absolute paths — and the question of whether llama.cpp's own flags should therefore be hashed through a normalised digest is handed back to the row epic named, not answered here. |
| Attached engines | An engine the harness does not spawn is checked, not trusted: before the run it reports what it has loaded, and a foreign model or concurrent client refuses the run. Energy is measured for the whole machine, so a daemon quietly serving something else attributes another workload's watts to this row. → PRD |
| Variant is a prompt transformation and nothing else | A variant transforms the prompt. It never changes the scorer, the expected output, the parser, the generation caps or the item set. A terse-output instruction that makes an answer unparseable scores 0 with its failure reason under Methodology 9, because "the compression made the model unparseable" is precisely the finding, and a parser loosened for one variant would destroy the comparison it was loosened to save. → PRD |
| Pairing is preserved by construction | Every variant runs every item of the suites it declares, recording a no-op where the transformation does not apply. E-G's paired test needs identical item ids across the compared arms; a variant permitted to skip items would produce a p-value over a set nobody declared. |
| Compressor cost is counted and kept separate | The `input_compressed` compressor runs inside the measured path, per item, with its own duration and energy on the row rather than merged into the generation's. An input compressor whose own cost is excluded looks free, and "compression saves tokens" is not a finding if the saving is paid for in seconds and joules somewhere the row does not show. → PRD |
| Prompt parity across engines is a gate, not an assumption | Before any cross-engine cell is published, the two engines' rendered prompts for the same model and item are compared byte for byte, and the result is recorded: identical, or divergent with the divergence named. Two engines rendering different prompts are not running the same experiment, and the difference would be read as an engine difference. Where the comparator cannot expose its rendered prompt at all, its rows carry that absence explicitly and its quality cells are published as observations rather than paired comparisons. → PRD |
| Thinking control is per engine as well as per model | The switch's spelling belongs to the engine registry entry beside the roster entry's declared control, and is verified the same way the roster epic verifies its own: by comparing the prompt rendered with the switch against the one rendered without it. Where an engine offers no control at all, its rows declare `allowed` honestly; a row publishing `disabled` under an engine that never sent anything is the exact class of unfalsifiable number both epics exist to remove. |
| A negative result is a result | If no variant produces a distinguishable difference, that is published with its intervals and its p-values as the answer to the research question. The epic's success evidence is that the question is answered, never that compression won. |

## Success Evidence

The campaign completes on the declared reference machine: two engines × four variants, across the roster and the suites that exist, every declared cell run and none left empty, and it produces a dated statement of whether each variant helped, hurt or was indistinguishable per task family, on quality, TTFT, tokens and energy — each difference carrying its paired test and its interval, or stated as an observation.

Beside it, four things that can fail:

- A row hand-built to claim `baseline` while carrying a transformed prompt is refused by the writer gate, and a row naming an engine absent from the registry is refused too. Verified against the gate, not by reading it.
- Two rows produced on one machine, one model and one variant by the two engines carry different fiche hashes, and a reproduction verdict between them returns `not comparable` naming the engine field rather than a false `not reproduced`.
- The parity check runs for at least one model and its result is published: the two engines' rendered prompts are identical, or the divergence is named and every quality cell it touches is published as an observation.
- The defaults side-run publishes its own figure on one named model, with the quant and context Ollama actually chose recorded beside the roster's, so the difference between "the engine" and "the engine as installed" is readable rather than argued.

Once `done`, record here what the answer to the research question actually was per task family, whether the ~8.5% figure from the coding-agent report transferred to models this size at all, whether Ollama exposed enough of its rendering and constraint machinery for a fair comparison or forced cells to be dropped, and whether the founding llama.cpp decision held on the numbers.

## Dependencies and Unknowns

| Item | Kind | Handling |
| --- | --- | --- |
| The row contract, the writer gate, the fiche registry and its hashing | dependency | `every-published-row-explains-and-reproduces-itself`. This epic adds fields to a contract and a projection that epic owns and ships. |
| Bootstrap intervals and the paired Wilcoxon over per-item scores | dependency | `a-score-is-published-with-its-interval-a-difference-with-its-test`. The research question is unanswerable without them: a variant difference stated without a paired test is an observation, and this epic's whole output is differences between variants. |
| The per-entry thinking control and the non-Qwen families | dependency, not blocking | `every-size-class-spans-two-families-or-says-it-does-not`. This epic can be built and demonstrated on the Qwen entries that exist; it declares the control per engine as well as per entry so the two meet cleanly when the roster grows. |
| The agentic harness dimension and the agentic suites | assumption | `no-use-case-is-silently-absent`. Accepted that the most interesting form of the research question — does compression help an SLM *in agentic work*, where contexts are long enough for input compression to mean anything — cannot be answered until those suites exist. This epic answers it for the task families that exist and says plainly which one it could not reach. |
| Whether Ollama can return the prompt as it finally rendered it | unknown | The highest-consequence unknown in this epic, because its answer decides whether cross-engine quality cells are comparisons or observations. Settled by a spike against a running instance before any cell is declared, not by reading documentation. The failure mode is handled either way by the parity-gate decision above. |
| Whether Ollama exposes grammar-constrained decoding, a schema-shaped substitute, or nothing | unknown | Spike, before the `constrained_output` × Ollama cell is declared. Three outcomes, all handled: the same mechanism (a real comparison), a different mechanism (recorded per row, published as a comparison of mechanisms), or none (the cell is dropped with its reason recorded, in the machine epic's discipline for a refused run). |
| Ollama's context default, and whether it silently truncates a prompt the reference engine did not | unknown | Spike, and treated as a correctness gate rather than a footnote. Methodology 3 requires the generation caps and context length to be identical across everything compared on an item; an engine that quietly applies a shorter context produces a worse number for a reason the row does not show, which is a fabricated comparison. The effective context is read back from the engine and asserted against the suite's declaration before the run. |
| Ollama's model-lifetime behaviour against the repetition protocol | unknown | Spike. A keep-alive or idle-unload shorter than the recorded cooldown would reload weights between counted repetitions and put load time inside a generation measurement, which corrupts the median rather than raising the spread flag. The setting is read, declared in the engine registry, and pinned for the run. |
| Whether an LLMLingua-2-class compressor fits on the reference machine beside the model under test | unknown | The compressor is itself a neural model competing for the same VRAM as a subject on a 6 GB laptop. Handled by declaring the compressor's placement (CPU, or a separate phase) in the variant entry and recording it on the row, so a reader knows whether its measured cost was paid on the same device as the generation. |
| Whether input compression is meaningful at all on short items | assumption | Accepted: it is not, and the applicability declaration exists to say so per suite rather than to quietly produce a null result. This is also why the interesting answer waits on the agentic and RAG suites. |
| Whether the ~8.5% token saving transfers from a frontier coding agent to an SLM | assumption | Accepted as a hypothesis to test, per the PRD's own wording, never as a baseline expectation. The epic is designed so the opposite result publishes as cleanly as the confirming one. |
| Ollama as a pinned, installable build | dependency | Named by the PRD as a dependency: "Availability of a second inference engine (Ollama) as a pinned, installable build alongside llama.cpp, since the engine comparison has no content without one." Pinned by version in the engine registry, and its version read by live probe rather than declared. |
| The engine comparison is single-machine | assumption | Accepted, per the campaign-shape decision. An engine that wins on a 6 GB laptop may not win on a no-GPU 16 GB machine, and this epic does not claim it does. Extending the two dimensions across machines is a later campaign, cheap once both dimensions are row fields. |

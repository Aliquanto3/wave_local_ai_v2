# Epic: Every size class spans two families, or says it does not

Given the published roster and the table built from it, every size class the three machines can hold either spans at least two model families — with dense and MoE both present where the class has both — or is labelled a single-family ladder, so no reader can mistake a comparison of quants within one vendor's model line for a comparison of the market.

## Context and Value

The audience is the one the PRD adds for the publication and names third in its Problem Statement: "an academic or technical reviewer of a published write-up, who judges the method rather than the verdict and expects sample sizes, statistical treatment, roster composition and licensing to hold up on their own." Roster composition is the half of that sentence no other epic owns. A reviewer handed four Qwen models and a table titled "small language models on ordinary hardware" does not dispute the numbers; they dispute that the table is about what it claims to be about. The gap brief states the same thing from the owner's side: "Four Qwen models. For a publication, at least two families are needed per size class" (gap 2), and puts it third in the priority order that gates every published run.

Verified current state, at `0f849c8`:

- **The roster is one family, four entries deep.** `aidd_docs/roster/models.json` at `roster_version: 2` holds `qwen3.6-35b-a3b-ud-iq4xs` (MoE, 40 experts, 3.1B active), `qwen3-0.6b-q8`, `qwen3-1.7b-q8` and `qwen3-4b-q4km`. Every published comparison this repository can currently produce is one vendor's model line at four sizes. Methodology 13's composition rule — "each size class it publishes spans at least two model families, and where a size class has both dense and MoE candidates, both are represented" — is satisfied by none of them, and there is nothing in the repository that says so.
- **The family field is half-declared, and deliberately optional.** The three dense entries carry `family: "qwen"`; the flagship carries none and resolves through the in-code fallback `roster.MODEL_FAMILIES` (`roster.py:76-82`), a state `tests/test_roster.py::test_the_shipped_moe_entry_still_loads_with_no_family_of_its_own` asserts on purpose. `family` is excluded from `REQUIRED_FIELDS` with its own comment explaining why: the shipped roster must keep loading and `roster_version` must not move, because published rows and `tests/test_reference_bundle.py` compare against it. So a new entry can be added today with no family at all and the file still loads.
- **Every candidate family is refused by the code that resolves families.** `KNOWN_FAMILIES` is `frozenset({"qwen", "mistral", "google"})` (`roster.py:69`), and `family_of` raises `RosterError` naming any value outside it. `gemma`, `granite`, `ministral`, `lfm2` and `phi` are all refusals today. The two non-Qwen members are there as *judge* families, and Methodology 11 has since retargeted the judge pair to Z.ai's GLM and DeepSeek and made Google and Mistral subjects only — so the set is stale in both directions.
- **There is no size class, and nothing from which one could be derived.** `grep -rn "size_class" src/` returns nothing. `architecture.active_params_b` is the only size-shaped field, and for the flagship it reads `3.1` against a model a machine must find ~15 GB for. No entry records total parameters or the file's size on disk, so nothing in the repository can group entries by what a machine has to hold — which is the only grouping the three declared machines make meaningful.
- **There is no licence field.** `grep -rn "licen" src/` returns only the suite-item literals `hand_written | licensed | public` in `classification_suite.py`, `translation_suite.py`, `judge_probe.py` and `suite_gate.py` — item provenance, not model licensing. The PRD's own Dependencies already ask for the other one: "Licence terms of each roster model permitting the client-side use the reproduction story asks for; a roster entry records the licence and whether client-side commercial use is permitted." Nothing records either.
- **No check gates the roster's composition.** `suite_gate.py` gates a *suite* on item count, language share and per-language cell size; nothing gates the roster. `tests/test_roster.py` asserts the shipped entries' identity fields — repo, revision, file, checksum, quant, architecture — and nothing about how the set is composed. The composition rule is prose in the PRD and prose in this file until it is a command that can exit non-zero.
- **The one thinking switch the code knows is a Qwen template convention.** `local_client._thinking_kwargs` maps `thinking_policy: disabled` to exactly `{"chat_template_kwargs": {"enable_thinking": False}}` (`local_client.py:74-75`), and the module docstring says why that spelling and no other: probed live on `b10537-bf0040e15` against `Qwen3-0.6B` and `Qwen3.6-35B-A3B`, where `reasoning_budget: 0` had no effect, `reasoning_format: "none"` only moved the envelope back into `content`, and `reasoning_effort: "none"` worked while the template's own `chat_template_caps` reported `supports_reasoning_effort: false`. `enable_thinking` is a kwarg a Jinja chat template either declares or silently ignores. A template that ignores it renders identically, the model reasons through its cap, and the row still publishes `thinking_policy: "disabled"` — required on every quality row since schema 11 (`row_contract.py:60,255`, written at `quality_cli.py:1091`). The first non-Qwen entry is the first row that can claim a policy the model never applied, and that is one function away.
- **The pinned build is a published comparability contract, not a dependency.** `docs/setup.md` step 2 is written entirely against `b10537` and states the rule plainly: "A different build is not wrong to use, but its results are not comparable to the committed evidence without saying so." The build string is no longer a source constant — `build_probe.probe_build` reads it off the binary (`__init__.py:251`) — so an upgrade propagates into the fiche automatically, and `llama_cpp_build` is the first of `verdict._RUNTIME_BLOCKING_FIELDS` (`verdict.py:24`). Upgrading to gain one family's architecture turns every published runtime row into `not_comparable`.
- **What a per-model entry actually costs is already measured.** The 2026-09-06 dense-ladder increment took four phases for three models of *one already-validated family*: download at a pinned commit sha and read the checksum off the file rather than the card, probe the real `-ngl` that launches under the 6 GB VRAM ceiling ("the model does not fit at -ngl 99 => -ngl is stepped down and the value that launched is recorded, not the value that was hoped for", phase-2), a single-model pilot before the matrix is paid for because a thinking-by-default model spends a 32-token cap on reasoning (plan.md:97), then the live runs. A new family adds two unknowns that ladder never faced: a chat template whose thinking control is unknown, and an architecture the pinned build may not implement at all.

The value is that this epic decides whether the publication has a subject. The machine epic makes the same suite run on three machines; the statistics epic puts an interval around each score; the judge epic makes an open-ended score admissible. All three improve the defensibility of a table whose rows are four Qwen models. A reviewer's first question about that table is not about intervals — it is whether "small language models on personal and professional PCs" was ever measured, or whether one vendor's ladder was measured and given a general title. The honest alternative is not silence: a size class that genuinely has one family is publishable *as a single-family ladder*, and saying so costs nothing and answers the objection. What is not publishable is the label's absence.

## Boundaries

- Includes: **the composition rule as an executable check** — a command that reads the roster and the published table, reports per size class the families it spans, whether dense and MoE are both present, and exits non-zero when a published table carries a single-family class without the single-family-ladder label. The check is the deliverable; the roster's content is what it is run against.
- Includes: **the size-class definition itself**, decided here as a fixed ordered vocabulary with boundaries drawn where the three declared machines stop being able to hold a model, and stated as revisable after the first full-roster run.
- Includes: **the roster fields the rule needs** — `family` resolvable for every entry the check classes, `size_class`, the footprint figures that justify the class (total parameters and the GGUF's size on disk beside the existing `active_params_b`), and the licence block: the licence id, whether client-side commercial use is permitted, and the date those terms were read.
- Includes: **a verification step per candidate model, as a gate rather than a report**, covering GGUF availability at a pinned revision with the checksum read off the downloaded file; the pinned build actually loading the architecture; the licence terms recorded; the chat template read from `/props` and its thinking control established through `/apply-template` the way the Qwen ladder's had to be; and the EN/FR/DE capability recorded as a sourced claim. A candidate that fails any of these does not enter the roster file.
- Includes: **candidate coverage across the gap brief's families** — Gemma 4 including the 26B-A4B MoE where the tower holds it, Granite at 350M and 1B, Ministral, LFM2 and Phi — pursued until the rule is satisfied in every class the machines can hold, not pursued as a fixed shopping list. The outcome is the composition, not a count of models.
- Includes: **a recorded refusal for every candidate that does not enter**, naming what it failed on — architecture unsupported by the pinned build, no GGUF at a pinned revision, a licence forbidding publication of results, an unverifiable thinking control. A class the check reports as single-family must be readable as *searched and found empty*, not as *not looked at*, which is the same discipline the machine epic applies to a refused run.
- Includes: **the existing suites re-run on the dev machine as each addition's acceptance** — classification and translation through the local chat path, producing rows that carry the new entry's family, size class and thinking policy. An entry that is authored but never run is a claim, not evidence.
- Includes: **the roster version bump and the `docs/setup.md` download section per model added**, following the pattern step 3.1 already establishes: `hf download <repo> <file> --revision <sha>`, then `Get-FileHash -Algorithm SHA256 ... .ToLower()` because `roster._SHA256_PATTERN` requires lowercase.
- Excludes: **run profiles, per-machine minimal requirements and machine fit.** `the-same-suite-runs-on-three-machines-or-names-why-it-cannot` owns the profile registry keyed by (roster entry x machine x compute mode) and the declared minimums, and states explicitly that minimums live in profiles, not in the roster. This epic produces the entries that registry is keyed on and declares nothing per machine. The size-class boundaries are informed by what the machines hold; the per-machine decision of whether a given entry runs is not taken here.
- Excludes: **judge family independence and the judge pair.** `any-open-ended-output-carries-two-judges-or-an-honest-flag` consumes `family`; this epic supplies it and grows `KNOWN_FAMILIES` so a non-Qwen subject resolves. Which judges score which subject, and the retargeting of that epic from Mistral and Google to Z.ai's GLM and DeepSeek under Methodology 11, are not this epic's.
- Excludes: **suite content, suite size, suite levels and inferential statistics** (gaps 3 and 7). More models multiply the rows a suite produces; they do not change what a suite contains.
- Excludes: **cloud subjects.** Mistral and Google are cloud subjects with their own clients and their own rows; the roster file is the local model registry and gains no cloud entry here.
- Excludes: **inference engines, agentic harnesses and prompt variants** (gaps 4 and 5). Each is a further row dimension multiplying this one; none of them is roster composition.
- Excludes: **the fiche mechanism, the row contract, the writer gate and the verdict logic.** The row epic owns them. This epic adds fields to a roster entry and inherits the republication discipline that follows; it rebuilds none of that machinery.
- Excludes: **rendering the composition to a reader at a glance.** `the-pitch-runs-from-a-browser-and-only-with-the-key` owns the views; this epic makes the class, the family and the ladder label exist and be correct on the data.
- Excludes: **the flagship entry's `revision: "main"` pin.** `aidd_docs/backlog/tech-debt.md` already carries it as an open row and states why it needs its own increment: it changes the entry whose byte-identical launch two tests and every published row depend on. Every entry this epic adds pins a sha; the flagship's is not retro-fixed here.
- Excludes: **re-deriving the Methodology's thresholds.** Taken as given.

### Decisions this epic takes

| Subject | Decision taken here |
| --- | --- |
| What a size class is measured in | **What a machine must hold, not what the model is nominally called.** A class is a declared field from a fixed ordered vocabulary, and its boundaries are drawn where the three machines separate. Classing by `active_params_b` would put the 26B-A4B MoE beside the 4B dense as if a reader could run them on the same machine; classing by total parameters alone ignores the quant that decides the footprint. The entry therefore declares the class *and* the two figures that justify it — total parameters and the GGUF's bytes on disk — so the classing is checkable against the entry rather than asserted by its author. → PRD |
| The initial boundaries | Four classes — roughly ~0.5B, ~2B, ~4B and ~8B-and-up by nominal size, bounded in practice by the footprint bands the 16 GB no-GPU PC, the 6 GB-VRAM laptop and the 8 GB-VRAM tower separate. Stated as revisable by a later decision, in the same sentence the PRD already applies to its other thresholds: they exist so the rule is falsifiable, not because the values are themselves evidence. → PRD |
| What the check refuses | **Silence, not the roster.** The rule cannot conjure a second family into a class that has none, so a check that refused a single-family roster would forbid an honest state. The check exits non-zero when a published table carries a single-family class *without* the label, when an entry it must class carries no resolvable family, size class or licence, and when a class declares a MoE absent with no reason recorded. A correctly labelled single-family ladder passes. |
| "Where the class has them" | A class declares whether a MoE candidate was sought and what was found. Methodology 13 conditions the dense-and-MoE requirement on the class having both, and an unqualified blank makes "this class has no MoE candidate" indistinguishable from "nobody looked". The absence is recorded with its reason, the way a refused run is. |
| Licence policy | **Any licence enters; the terms are published per entry.** A candidate is not excluded for a restrictive licence: the entry records the licence id, whether client-side commercial use is permitted, and the date the terms were read, and the published table carries them, so a reader sees which rows they may act on. The one refusal is a licence that forbids publishing benchmark results of the model at all — that makes the row unpublishable rather than merely unusable. Recording the retrieval date follows the discipline Methodology 16 already applies to a list price: terms move, and a row says when it read them. → PRD |
| The thinking control is per entry, declared and verified | `enable_thinking` is a Qwen template convention that a template silently ignores when it does not declare it, and the row would still publish `thinking_policy: "disabled"`. An entry therefore declares the thinking control that works for its template — or `none` where the model does not reason — and the disabled policy is *verified* by comparing the string `/apply-template` returns with the switch against the one it returns without it. A model whose control cannot be verified enters with `allowed` declared honestly, or does not enter. A row claiming a policy the model did not apply is the exact class of unfalsifiable number the row epic exists to remove. → PRD |
| Unsupported architecture: defer by default | When the pinned `b10537` does not implement a candidate's architecture, the default is **defer the model and record the refusal**, naming the architecture and the build. Upgrading the pinned build is available but is not a per-model decision: `llama_cpp_build` is verdict-blocking (`verdict.py:24`) and `docs/setup.md` states that a different build's results "are not comparable to the committed evidence without saying so", so an upgrade turns every published runtime row `not_comparable` and forces a republication of the runtime reference bundle under the row epic's supersede-don't-backfill rule — retained, marked with the schema and build that produced them, never back-filled. If an upgrade is taken it is taken **once for the whole roster**, before the campaign, never mid-roster and never per model. The story that first hits an unsupported architecture names the tradeoff and the owner decides; it does not slip the upgrade in as a fix. |
| EN/FR/DE capability is a claim, not a measurement | The entry records the language claim and its source. The suites are what test it, afterwards. An entry whose claim the suite rows contradict stays in the roster with the contradiction published — that is a finding about the model, and removing the entry would delete the evidence for it. |
| Family resolution for the flagship | The check requires every entry to *resolve* a family through `roster.family_of`, which the flagship does through the in-code fallback. No exception is carved out and `REQUIRED_FIELDS` does not move, so the shipped entry keeps loading and `tests/test_reference_bundle.py` keeps passing. Every entry this epic adds declares `family` in the file. |

## Success Evidence

The proving pass: the composition check exists, disagrees with the roster as it stands today, and then agrees with it after the entries land — and at least one non-Qwen family has produced real rows from the existing suites on the dev machine.

Seven checks, each able to fail. The first five are code-level and run against constructed rosters and stubbed servers; the last two need the dev machine and downloaded weights.

- Run against the **shipped roster as it is today**, the check reports four size classes, each spanning exactly one family, and exits non-zero because no published table carries the single-family-ladder label. This is the check's calibration and it must produce that answer *before* any new entry is authored — a check that passes on a four-Qwen roster is not checking the rule.
- A constructed roster in which one class holds two families passes for that class; the same roster with the second family removed and the label added passes as a labelled ladder; with the second family removed and the label absent, it exits non-zero naming the class. Three outcomes from one rule, each reachable.
- An entry carrying no resolvable family, no size class, or no licence block is named by the check rather than skipped, and an entry whose declared size class disagrees with the footprint figures it declares is named too — so the classing is falsifiable from the file.
- A class declaring no MoE representation with no reason recorded exits non-zero; the same class with the absence and its reason recorded passes.
- A constructed entry declaring a thinking control its template does not honour is refused by the verification step, because the prompt `/apply-template` renders with the switch is byte-identical to the one it renders without it — verified against a stubbed `/props` and `/apply-template`, not by reading the guard.
- On the dev machine, at least one non-Qwen entry downloads at its pinned revision, hashes to its declared `sha256`, launches under the pinned build, and runs the classification and translation suites to completion, producing rows whose `family` is not `qwen` and whose `thinking_policy` matches what the template demonstrably did.
- Handed the published table and the roster file and nothing else, a reader can name, for each size class, which families it spans, whether it is a single-family ladder, whether a MoE is represented and why not where it is not, and under which licence each model's results may be reused. No part of that answer requires reading this repository's source.

Once `done`, record here which candidates were refused and on what — architecture, licence, template or availability — which classes ended up as labelled single-family ladders, whether the pinned build held for every family that entered, and whether the four class boundaries survived contact with the three machines.

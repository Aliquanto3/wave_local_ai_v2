# Spike: Is Z.ai's GLM callable as a pinned judge, and on what data terms

## Question

Does Z.ai's direct API expose a GLM model that can be pinned to a dated id from a live catalog, called with reasoning disabled or minimal under caller-pinned sampling, survived on its paid tier's rate limits, and costed from a published list price, and do Z.ai's data-use and retention terms let the repo's suite items and a local model's output be sent to it?

## Decision

Go or no-go for the GLM judge client (order 8), and its build inputs: the pinned id and its build markers (Methodology 12 as amended by owner answer Q102 (a), 2026-10-03), the sampling set and seed availability, the reasoning control and the effort value it sends, the finish-reason mapping, the rate-limit status and retry-hint shape, the list-price entry, and the data-use sentence the README's egress statement carries. Terms incompatible with the PRD's egress non-goal are a finding that reopens the judge pair, not a detail.

## Bounds

- Evidence needed: captured live requests and responses, never a documentation page alone, for each of the questions the completed Google spike answered (`aidd_docs/backlog/spikes/google-ai-studio-api-surface-is-confirmed-live.md`): live catalog endpoint and auth, and the shape of one entry; whether dated non-floating ids are listed and addressable, and which alias each resolves from; sampling parameter names, ranges and the values applied when omitted; whether a per-request seed exists and is honoured (repeated calls with and without it); where the content, finish reason and usage counts live, the full finish-reason enum with its block or safety values, and whether reasoning tokens are reported apart from output tokens; the reasoning or thinking control, whether it can be disabled, and what is billed when it is; the paid tier's rate limits, the status and body of a limit response and any retry-after hint; the API version a row records and where it is read; catalogue input, output and reasoning rates for the pin candidate, with source URL and retrieval date; Z.ai's data-use and retention terms for API traffic at a named revision, including whether submitted text is used for training. The precedent `mistral_client.py` records stands: a documented id that is absent from the live listing is recorded as that failure.
- Stop when: one pin candidate is named under Methodology 12 as amended by owner answer Q102 (a), 2026-10-03: the release or snapshot id Z.ai serves (it publishes no dated id for a judge-grade model), checked against the live model list if one exists or otherwise by a one-token probe to that id, plus every build marker the live calls capture (the response's `model` field and any version header), with every build input above answered from a captured call and the terms stated from their text; or the API is shown unable to meet that pre-flight (neither a listing nor a successful probe for the id) or the egress non-goal, which is recorded as a no-go.

## Outcome

- Result: desk research settles the documented surface and the data terms; it cannot settle the Bounds, which demand captured calls, and two findings put Methodology 12 at risk.
  - Platform: the story's "Z.ai's own direct API" is read as Z.ai international, `https://api.z.ai/api/paas/v4`, token-priced, not the Coding Plan endpoint and not bigmodel.cn (Assumption A1).
  - Live catalog: none documented. If `GET /api/paas/v4/models` does not exist live, Methodology 12's pre-flight was unimplementable on this provider as written (Q102). Owner answer Q102 (a), 2026-10-03, amended it: without a model list, a one-token probe to the pinned id is the pre-flight, recorded on the row as a probe.
  - Dated ids: none for any current GLM text model. The only dated id, `glm-4-32b-0414-128k`, is an April 2025 model without thinking control. Every judge-grade id is a release id (`glm-5.2`), and no snapshot or deprecation policy is published, so a silent weight change behind a release id is not excluded by any text (Q102). Owner answer Q102 (a), 2026-10-03: the release id is pinned with every build marker the provider returns, a run refuses when a marker differs, and a weight change under an unchanged id and marker is accepted as undetectable, with the inter-judge agreement and the calibration figures as the drift signals.
  - Pin candidate (desk, provisional): `glm-5.2`. Reason: the newest GLM text model whose thinking can be disabled; `glm-5.3` and `glm-5.3-flash` are excluded because "use forced thinking and cannot be disabled", which breaks the story's "disabled or minimal" binding. Fallback on cost: `glm-4.7`. List price, retrieved 2026-10-02 from https://docs.z.ai/guides/overview/pricing.md: `glm-5.2` $1.40 input, $0.26 cached input, $4.40 output per 1M tokens; `glm-4.7` $0.60, $0.11, $2.20. No separate reasoning rate is published.
  - Sampling set: `temperature` [0.0, 1.0] (default 1.0 on 5.x and 4.7), `top_p` [0.01, 1.0] (default 0.95), `max_tokens` [1, 131072], `do_sample` (default true). No per-request seed exists in the reference. The documented determinism control is `do_sample: false` (greedy, temperature and top_p ignored); whether it yields byte-identical repeats is unproven.
  - Reasoning control: `thinking.type: "disabled"`; there is no effort level, so the recorded effort is `disabled`. Billing of reasoning tokens and whether usage reports them apart from `completion_tokens` are undocumented; no reasoning-token usage field is documented.
  - Finish reasons (6, documented): `stop` => completed; `length` => caller's cap reached; `model_context_window_exceeded` => model's context limit reached; `sensitive` => blocked (fail the call, reason named verbatim); `tool_calls` => other; `network_error` => other, and recommended as a failed retryable call, never scored (Assumption A4). Methodology 9's two truncation causes are distinguishable on paper.
  - Rate limits: per-account, per-model concurrency, figures only in the login-gated console. 429 with body `{"error": {"code": "1302", "message": "Rate limit reached for requests"}}`; 1305 overload; 1308 and 1310 carry a reset time inside the message text; 1113 is insufficient balance and must not be retried. No `Retry-After` header is documented.
  - API version: path segment `paas/v4`; the OpenAPI reference states `1.0.0`. The row should record `paas/v4` (Assumption A3) unless a live response carries a version header.
  - Data terms, Z.ai international: Terms of Use (Last Update April 14, 2026), Additional Terms for API Services 3(b): API content is used only to provide the service, comply with law, enforce policies and prevent abuse, and "We will not use End User Content for developing or improving Services, unless you explicitly agree to such use." DPA for API Services (in the Privacy Policy, Last Update September 29, 2025): content "is processed in real-time ... and is not saved on our servers"; services generally provided from Singapore. No retention period and no zero-retention contract are published; the DPA's "delete such data after the termination of the Terms" sentence sits awkwardly beside "do not store", and is read as covering account personal data (Assumption A5). These terms are compatible with the PRD egress non-goal: only repo suite items and outputs derived from them leave the machine, and the non-goal sets no destination restriction. No terms conflict, so no owner question on terms.
  - bigmodel.cn, for the record: Beijing entity, mainland-China storage, anonymised data may train models. If the client were ever pointed at `open.bigmodel.cn`, the egress sentence below would be wrong.
  - Proposed README egress clause for Z.ai: "Z.ai (JINGSHENG HENGXING TECHNOLOGY PTE. LTD, Singapore) receives suite items and subject outputs for judging; its API terms (Terms of Use, April 14, 2026; Data Processing Addendum for API Services, September 29, 2025) state that API content is not used to develop or improve its services without opt-in and is processed in real time without being saved."
- Confidence: high on the documented parameters, finish-reason enum, error codes, prices and terms text (primary pages, quoted). Low on everything the Bounds require from a live call: listing existence, alias resolution, determinism, reasoning-token reporting and billing, actual 429 headers.
- Remaining uncertainty:
  - Whether `GET https://api.z.ai/api/paas/v4/models` exists, its auth, and its entry shape; whether `glm-5.2` and `glm-4-32b-0414-128k` appear in it.
  - Whether a response reveals the build behind `glm-5.2` (a `model` field differing from the request, or a version header).
  - Whether `seed` is rejected (error 1214) or silently ignored; whether `do_sample: false` gives byte-identical repeats.
  - Whether `thinking: disabled` yields zero reasoning content and tokens on `glm-5.2`, whether `usage.completion_tokens_details.reasoning_tokens` exists, and whether reasoning tokens are inside `completion_tokens` (billed as output).
  - Per-model concurrency on the paid account, the 429 response headers, and whether any retry hint exists beyond 1308 and 1310 message text.
  - Error code and HTTP status for an unknown model id, and for an input-side content block.

Decisions (already taken, not re-asked): judge pair is Z.ai GLM and DeepSeek through each provider's own direct API (PRD Methodology 11); outputs derived from repo suite items may be judged (epic assumption row, accepted); a small judging budget of about ten dollars per campaign (PRD Dependencies); a documented id absent from the live listing is recorded as that failure (`mistral_client.py` precedent, cited in Bounds).

Assumptions: A1 Z.ai international is meant, from the story's wording "Z.ai's own direct API" and "a paid API key (Z.ai)". A2 `glm-5.2` as provisional pin candidate on judge capability and thinking control, not on measured judge quality. A3 `paas/v4` is the API version a row records. A4 `network_error` is treated as a failed retryable call. A5 the DPA's deletion-on-termination sentence covers account personal data, not request content.

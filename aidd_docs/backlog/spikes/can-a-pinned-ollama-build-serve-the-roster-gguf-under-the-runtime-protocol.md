# Spike: Can a pinned Ollama build serve the roster's own GGUF under the runtime protocol

## Question

Can a pinned, installable Ollama build on the reference machine load a roster entry's own GGUF file with a checksum a run can match against the entry's `sha256`, report its own version, its effective context and every configuration default it applies, show what it has loaded and whether another client is using it, and keep the model loaded across the runtime protocol's warm-up, counted repetitions and recorded cooldowns without a silent reload?

## Decision

Whether Ollama can be registered as the `attached` comparator engine entry (order 6) and with which build inputs: the pinned version and the live endpoint that reports it; the health and chat endpoints and the default port; how a model definition points at a roster GGUF and whether `artifact_parity: same_gguf` is reachable, or only `engine_supplied`; the endpoint that lists loaded models and whether concurrent clients are observable at all; the keep-alive setting, its default, and how it is pinned for a run; the effective context the engine reports and whether a prompt longer than it is truncated silently or refused; the per-generation timings it reports and whether its first-token time is server-reported (Methodology 20); and the thinking control's spelling, if any. The same answers fix what the defaults side-run (order 11) records about a default install: its quant choice, its context default and whether a library tag matches a roster entry.

## Bounds

- Evidence needed: captured live requests and responses against a running instance of a named, pinned Ollama version on the reference machine, never a documentation page alone (the epic's rule for these unknowns). For `qwen3-0.6b-q8`: a model created from the roster entry's own file and the checksum the engine reports or the file it reads; the version endpoint's response; the loaded-model listing before, during and after a run; whether a second client's request is visible from the harness side; generation timings across a warm-up plus five counted repetitions separated by the 10 s default cooldown, with any reported load duration per repetition; the configured and the reported context, and the result of one prompt deliberately longer than the default context; the configuration defaults the server reports for the loaded model, each marked engine-reported or not reported; whether the Qwen thinking control is forwarded, spelled as its own parameter, or absent. For the defaults side-run: the quant and context a default install picks when the matching library tag is pulled, and whether a tag exists for the MoE flagship (input to Q21).
- Stop when: each build input above is answered from a captured call, or Ollama is shown unable to hold the model loaded across the protocol, unable to report its version by live probe, or unable to state its effective context; any of these three is recorded as the finding that blocks the comparator entry, with the evidence.

(2) With `OLLAMA_DEBUG=1` the server log carries the full `llama-server` argument list, which would let a run record the applied configuration as engine-reported rather than declared. (3) The reference machine has less than 24 GiB VRAM, so a default install's context is 4096. (4) `shift: false` plus `truncate: false` makes an over-long single-message prompt an HTTP 400 rather than a truncation.

## Outcome

- Result: blocked on the live run the Bounds require. Desk research settles every build input except what only a captured call can show: pin `v0.35.1` (zip per tag, hash in `sha256sum.txt`); version probe `GET /api/version`; health `GET /` ("Ollama is running"); chat `POST /api/chat`; default port 11434; `artifact_parity: same_gguf` reachable by `FROM <roster file>`, because the model layer digest is the file's SHA-256; loaded models from `GET /api/ps`, whose `context_length` is the engine-reported effective context; concurrent clients not observable through any endpoint; keep-alive default `5m`, pinned per request with `keep_alive: -1`; timings `load_duration`, `prompt_eval_duration`, `eval_count`, `eval_duration`, where `prompt_eval_duration` is the bundled llama-server's `prompt_ms`, server-reported on the same definition as the llama.cpp rows' TTFT; thinking control spelled `think`. Default install (side-run): `qwen3:0.6b` resolves to Q4_K_M, context set by VRAM (4096 under 24 GiB), and no library tag holds the roster's Q8_0 file or the MoE flagship's UD-IQ4_XS quant.
- Confidence: high for API shape, digest semantics, defaults and library tags (read in pinned source and live pages); medium for the native-mode routing of the imported Qwen3 GGUF and for the over-long-prompt behaviour (inferred from source, not observed).
- Remaining uncertainty: the captured checksum, version response, `/api/ps` before, during and after a run, a second client's visibility, timings over a warm-up plus five counted repetitions with 10 s cooldowns and no reload (`load_duration` near zero after warm-up), the over-long prompt's response, the `/api/show` template/renderer fields, and the default-install quant and context, all from one live session:

```powershell
$v='v0.35.1'; $d="D:\ia\ollama-$v"; $h='http://127.0.0.1:11500'
curl.exe -L -o "$d.zip" "https://github.com/ollama/ollama/releases/download/$v/ollama-windows-amd64.zip"
curl.exe -L -o "$d-sha256sum.txt" "https://github.com/ollama/ollama/releases/download/$v/sha256sum.txt"
(Get-FileHash "$d.zip" -Algorithm SHA256).Hash   # must equal the ollama-windows-amd64.zip line
Expand-Archive "$d.zip" $d
$env:OLLAMA_HOST='127.0.0.1:11500'; $env:OLLAMA_MODELS="$d-models"; $env:OLLAMA_DEBUG='1'; $env:OLLAMA_FLASH_ATTENTION='1'
Start-Process "$d\ollama.exe" serve -RedirectStandardError "$d-serve.log"
curl.exe -s "$h/api/version"; curl.exe -s "$h/"
Set-Content "$d-Modelfile" 'FROM D:\ia\models\Qwen3-0.6B\Qwen3-0.6B-Q8_0.gguf'
& "$d\ollama.exe" create wla-qwen3-0.6b-q8 -f "$d-Modelfile"
Get-Content "$d-models\manifests\registry.ollama.ai\library\wla-qwen3-0.6b-q8\latest"  # model layer must be sha256:9465e63a22add5354d9bb4b99e90117043c7124007664907259bd16d043bb031
curl.exe -s "$h/api/show" -d '{"model":"wla-qwen3-0.6b-q8"}'  # expect empty template, renderer, parser
curl.exe -s "$h/api/ps"                                        # before the run: empty
```

The separate port and model store leave `D:\ia\ollama` and any running Ollama app untouched. Each generation (a warm-up plus five counted, `Start-Sleep 10` between, `curl.exe -s "$h/api/ps"` after each) posts to `$h/api/chat`, with options mirroring the roster `server_flags` and the suite's generation constraints:

```json
{"model":"wla-qwen3-0.6b-q8","stream":false,"think":false,"keep_alive":-1,"shift":false,"truncate":false,
 "messages":[{"role":"user","content":"<classification item prompt>"}],
 "options":{"num_ctx":32768,"num_gpu":99,"num_batch":512,"seed":<suite seed>,"temperature":<suite>,"top_k":<suite>,"top_p":<suite>,"num_predict":<suite max_output_tokens>}}
```

Then: one request whose user message exceeds 32768 tokens (record status and body); one request from a second shell during a counted repetition (record whether `/api/ps` or any response shows it); the `llama-server` argument line from `$d-serve.log`. Defaults side-run, in a fresh `OLLAMA_MODELS`: `& "$d\ollama.exe" pull qwen3:0.6b`, then the same body with `"options":{}` and no `keep_alive`; record `/api/show` `details.quantization_level` and `/api/ps` `context_length`.

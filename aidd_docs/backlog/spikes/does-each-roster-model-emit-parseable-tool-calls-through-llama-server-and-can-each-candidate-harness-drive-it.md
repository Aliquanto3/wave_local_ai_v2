# Spike: Does each roster model emit parseable tool calls through llama-server, and can each candidate harness drive it?

## Question

For each roster GGUF, does its chat template, served by the pinned llama-server build through `/v1/chat/completions` with `--jinja` and a `tools` array, return tool calls the server parses into structured `tool_calls`, and when it does not, is the failure attributable to the model or to its template? And for each of `smolagents`, `langgraph`, `pydantic-ai` and `llamaindex`: does it drive a local llama-server endpoint at all, does it surrender its call sequence in a transcript shape comparable to `direct`'s, and is its per-call prompt overhead readable rather than inferred?

## Decision

Whether agentic tool calling and agentic planning are built as suites or marked `out-of-scope-this-release` with this spike's finding published as the reason (the epic's first conditional trigger); per roster model, whether its rows are evidence of the model or of its template; and which candidate frameworks are comparable, which are recorded as unmeasurable, and whether the harness comparison is out of scope with `direct` published as the lone reference (the epic's third conditional trigger).

## Bounds

- Evidence needed: per roster entry in `aidd_docs/roster/models.json`, a small fixed set of tool-calling probes (single call, call with typed arguments, no call expected, two sequential calls) run against the pinned build, recording the raw response, whether `tool_calls` was populated, and the template in force (`local_client.chat_template`); for a failure, the same probe under a known-good template or against the model's documented tool format, to separate model from template; per framework, its pinned version, whether it accepts an OpenAI-compatible base URL pointed at llama-server, the call sequence it exposes after one probe, and whether the prompt the engine received can be read (server-side prompt logging or the framework's own trace) to compute overhead.
- Stop when: every roster model has a parseable, failing-model or failing-template verdict on the probe set, and every candidate framework has a verdict on the three questions, or a dependency (an unpinned build, a framework that cannot be installed under the lockfile) stops the next check.

### Evidence

- Engine path per roster entry at b10537. Qwen3-0.6B, 1.7B and 4B share one embedded template (Hermes-style JSON inside `<tool_call>`); it reaches the differential autoparser, `JSON_NATIVE` mode. That template is not in b10537's tool-call tests, though its format family (Hermes 2 Pro) is. Qwen3.6-35B-A3B's embedded template (Unsloth-modified, Qwen3-Coder XML) reaches the dedicated Qwen3-Coder handler, whose format (via Qwen3.5-4B) is unit-tested with thinking disabled and with parallel calls.
- `docs/function-calling.md` at b10537 describes a handler table the code no longer has. Which path the server took for a model is readable only from a `-lv 5` server log ("Using specialized template: Qwen3-Coder" or "using differential autoparser"), not from the docs.
- The roster's `enable_thinking: false` combined with a forced `tool_choice` (`required` or named) is an open, unfixed llama.cpp defect for Qwen3-family templates (#27767). `tool_choice: auto` is unaffected. smolagents sends `required` by default. pydantic-ai sends `required` only for a structured `output_type`.
- A request can ask the server not to parse (`parse_tool_calls: false`; server-wide `--skip-chat-parsing`). The raw text the model emitted under the same rendered prompt is then returned as content. That splits model failure from parser failure without a second model or template.
- All four frameworks accept an OpenAI-compatible base URL, and all four use native `tools` / `tool_calls` in the configurations named above (smolagents `ToolCallingAgent`, not `CodeAgent`; LlamaIndex only with `is_function_calling_model=True`). None of them needs prompt-based ReAct to reach llama-server.
- Each framework exposes its own call record: smolagents `memory.steps[*].model_input_messages` / `model_output_message`, pydantic-ai `result.all_messages()`, LangGraph state `messages` (`AIMessage.tool_calls`, `ToolMessage`), LlamaIndex workflow events. These are four different shapes. All four send through the `openai` Python client over HTTP, so a recording reverse proxy between the harness and llama-server captures every request body and response in one shape for every harness, `direct` included.
- The engine-side prompt per call is readable without trusting a framework. Q33 (a) needs two counts. The engine count is the response's `usage.prompt_tokens`. The rendered prompt is the captured request's `messages` + `tools` + `chat_template_kwargs` replayed through `/apply-template`, and the project already verified on b10537 that this matches `usage.prompt_tokens`, tools included. This is framework-independent.
- Framework behaviours that change the comparison and must be recorded per row: smolagents adds a `final_answer` tool, its own system prompt, tools duplicated as text, a `"New task:\n"` prefix and stop sequences, and it makes a no-call answer impossible (every turn is a tool call); LlamaIndex defaults to streaming and to `parallel_tool_calls: true`, which changes the server grammar (`max_calls` unbounded) relative to `direct`; pydantic-ai with `output_type=str` adds nothing but its tool schemas generated from Python signatures; LangGraph's behaviour depends on `langchain-openai`'s version as much as on `langgraph`'s.

### Decisions

- Methodology 23 (PRD line 68): candidate set closed at `direct`, `smolagents`, `langgraph`, `pydantic-ai`, `llamaindex`; at most 3 per campaign; `llamaindex` mandatory for RAG answer generation. Mirrored in `src/wave_local_ai_v2/harness.py`.
- Q33 (a), owner answer 2026-10-01: overhead per call = engine-received prompt tokens minus the item's own rendered prompt tokens (the item's tool definitions as rendered under `direct` count as item), same tokenizer; a harness that rewrites rather than wraps is recorded unmeasurable, never zero.
- Q34 (a), owner answer 2026-10-01: web research is pipeline-first, records harness `direct`, and is independent of this spike.
- Roster: every entry launches with `--jinja` and requests `chat_template_kwargs.enable_thinking: false` (`aidd_docs/roster/models.json`).
- Q109 (a), owner answer 2026-10-03: each harness adapter keeps its framework's request defaults; the row records the `tool_choice`, `parallel_tool_calls` and `stream` actually sent, read from the captured request; a failure caused by an engine defect under those defaults is published as a harness-by-engine finding.
- Q110 (c), owner answer 2026-10-03: a new row field `harness_client_version` names the client package that built the engine request (`langchain-openai` for `langgraph`, `llama-index-llms-openai-like` for `llamaindex`), null for `direct`, `smolagents` and `pydantic-ai`; order 7 carries it with its schema bump, and the done harness task is not reopened. Order 7's adapter also reconciles `harness.HARNESS_DISTRIBUTIONS["pydantic-ai"]` with the `pydantic-ai-slim` install this spike probes.

### Assumptions

- The roster's `UD-IQ4_XS` file embeds the same template as the GGUF whose metadata the hub API returned (same repo revision, same conversion run). The live `/props` read settles it.
- #27767 is still present at b10537. It was open on 2026-10-02 with no fix PR, and b10537's Qwen3-Coder handler shows no special case for it.
- The autoparser classifies the dense Qwen3 template as `JSON_NATIVE` with `<tool_call>` section markers, by analogy with the tested Hermes 2 Pro template, which renders the same call shape. Untested at b10537 for this exact template, so it may throw at analysis or mis-detect the reasoning markers.
- Re-serialized tool schemas (pydantic-ai from Python signatures, smolagents from its `inputs` dict, LlamaIndex from a function schema) will not be byte-identical to the item's JSON; LangChain `bind_tools` passes OpenAI-format dicts through. Whether that difference counts as "wrapping" (positive overhead) or "rewriting" (unmeasurable) is read per call by the Q33 rule. It is not decidable from the docs.
- `langgraph.prebuilt.ToolNode` / `tools_condition` remain exported by `langgraph-prebuilt` 1.1.0 (only `create_react_agent` is deprecated).

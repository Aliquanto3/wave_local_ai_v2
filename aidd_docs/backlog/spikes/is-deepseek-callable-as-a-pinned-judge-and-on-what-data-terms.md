# Spike: Is DeepSeek callable as a pinned judge, and on what data terms

## Question

Does DeepSeek's direct API expose a model that can be pinned to a dated id from a live catalog, called with reasoning disabled or minimal under caller-pinned sampling, survived on its paid tier's rate limits, and costed from a published list price, and do DeepSeek's data-use and retention terms let the repo's suite items and a local model's output be sent to it?

## Decision

Go or no-go for the DeepSeek judge client (order 9), and its build inputs: the pinned id and its build markers (Methodology 12 as amended by owner answer Q102 (a), 2026-10-03), the sampling set and seed availability, the reasoning control or the model choice that disables reasoning and the effort value recorded for it, the finish-reason mapping, the rate-limit status and retry-hint shape, the list-price entry, and the data-use sentence the README's egress statement carries. Terms incompatible with the PRD's egress non-goal are a finding that reopens the judge pair, not a detail.

## Bounds

- Evidence needed: captured live requests and responses, never a documentation page alone, for each of the questions the completed Google spike answered (`aidd_docs/backlog/spikes/google-ai-studio-api-surface-is-confirmed-live.md`): live catalog endpoint and auth, and the shape of one entry; whether dated non-floating ids are listed and addressable, or only aliases, and which version an alias serves on the day it is called; sampling parameter names, ranges and the values applied when omitted; whether a per-request seed exists and is honoured (repeated calls with and without it); where the content, finish reason and usage counts live, the full finish-reason enum with its block or safety values, and whether reasoning tokens are reported apart from output tokens; how reasoning is disabled or minimised and what is billed when it is; the paid tier's rate limits, the status and body of a limit response and any retry-after hint; the API version a row records and where it is read; catalogue input, output, cache-hit and any time-of-day rates for the pin candidate, with source URL and retrieval date; DeepSeek's data-use and retention terms for API traffic at a named revision, including whether submitted text is used for training and where it is processed. The precedent `mistral_client.py` records stands: a documented id that is absent from the live listing is recorded as that failure.
- Stop when: one pin candidate is named under Methodology 12 as amended by owner answer Q102 (a), 2026-10-03: the release or snapshot id DeepSeek serves (it publishes no dated id) read from the live `/models` list, plus every build marker the live calls capture (the listing's `name`, the response's `model` and `system_fingerprint`), with every build input above answered from a captured call and the terms stated from their text; or the API is shown unable to meet that pre-flight (the id absent from the live list, or no stable marker to refuse on) or the egress non-goal, which is recorded as a no-go.

### Evidence

- The live catalog endpoint is documented (`GET /models`), but its documented entries carry only floating names (`deepseek-flash`, `deepseek-v4-pro`) and a display `name` without a date. The only dated string, "DeepSeek-V4-Pro-0813", is a documentation label, not an addressable id.
- DeepSeek's documented versioning practice is in-place repointing of names, including a weight update under an unchanged `deepseek-v4-pro` on 2026-08-13 and a family swap under `deepseek-flash` on 2026-09-10.
- Non-thinking mode is selected per request (`thinking.type: disabled` or `reasoning_effort: none`), not by a separate model. In non-thinking mode `temperature` applies and `top_p` is ignored (fixed at 1.0); in thinking mode the reverse holds. No per-request seed is documented.
- `length` is the only token-limit finish reason; no separate context-limit value, and no block value besides `content_filter`, is documented.
- Rate limiting is per-model concurrency with 429 and no documented retry hint; queued requests may receive whitespace keep-alives for up to 10 minutes before inference starts.
- API Inputs are covered by a privacy policy that permits training use by default, offers an opt-out by email, stores and processes in the PRC, and sets no fixed retention period.

### Decisions

- Methodology 12 (PRD line 57) and the parent story's first acceptance bullet: a documentation-sourced id is never pinned; "If the spike finds that the catalog exposes only floating ids, the story stays blocked." Superseded by owner answer Q102 (a), 2026-10-03, which amended Methodology 12: where no dated id is published, the release or snapshot id is pinned from the live list, every build marker the provider returns is recorded, and a run refuses when a marker differs from the pinned one; a weight change under an unchanged id and marker is undetectable, and the inter-judge agreement and the calibration figures are the drift signals.
- Training opt-out, owner answer Q103 (c), 2026-10-03: the owner emails privacy@deepseek.com requesting it before the first paid call, and the README states that it was sent, its date, and whether DeepSeek confirmed it.
- Methodology 11 (PRD line 56): DeepSeek is called through its own direct API; a third-party host of DeepSeek weights is outside the current methodology.

### Assumptions

- The live `/models` response matches the documented example (only the two floating ids). This is the single fact that decides go or no-go and must be captured live.
- "Personal Data" in the privacy policy is read as including API Inputs, because the policy defines Inputs as prompts submitted to the Services and the Open Platform terms defer to it. The repo's suite items are not personal data, so whether the training clause legally reaches them is unclear; the conservative reading is that they may be used for training.
- Pin candidate, now that owner answer Q102 (a) accepts a release id: `deepseek-v4-pro` over `deepseek-flash`, because Flash's name was repointed to a new model three weeks ago and its legacy names already route elsewhere.
- Peak-or-off-peak pricing depends on the UTC request time and the Chinese public-holiday calendar, which the docs do not publish in machine-readable form; costing every call at the peak rate is a safe upper bound.

## Outcome

- Result: likely no-go under Methodology 12 as written, pending one live call. DeepSeek's documented catalog lists only floating names, and its change log shows the names are repointed in place, so no dated id can be pinned or checked against the live list. Every other build input is documented and workable: `GET /models`; reasoning disabled per request via `thinking.type: disabled` (effort recorded as `none`); `temperature` 0 to 2 and `max_tokens` caller-pinned, `top_p` ignored in non-thinking mode; no seed; finish reasons `stop`, `length`, `content_filter`, `tool_calls`, `insufficient_system_resource`, `aborted`; reasoning tokens at `usage.completion_tokens_details.reasoning_tokens`; concurrency limit 500 on `deepseek-v4-pro`, 429 with no documented retry hint; no documented API version; list price for `deepseek-v4-pro` $1.32 / $3.96 per 1M input / output at peak, $0.044 cache hit, off-peak half.
- Terms: API Inputs may be used for training by default (opt-out by email to privacy@deepseek.com), are processed and stored in the PRC, and are retained "as long as necessary" with no fixed period (Privacy Policy, last update 2026-02-10; Open Platform Terms effective 2026-04-29). This is compatible with the PRD's egress non-goal as written, which lets the repo's own suite items leave the machine and constrains only client material. It is not a no-go on data terms, but the README's egress sentence must state all three.
- Confidence: high on the documentation facts (primary DeepSeek pages read directly); medium on the go/no-go, because the Bounds require the catalog shape to be captured live and documentation examples can lag the live service.
- Methodology 12 since owner answer Q102 (a), 2026-10-03: the "likely no-go" reading above applied the text as then written. The amended rule pins the release id (`deepseek-v4-pro`) from the live list with every build marker the provider returns, so go or no-go now rests on the live calls alone.
- Remaining uncertainty: the live `/models` ids; whether a dated id such as `deepseek-v4-pro-0813` is addressable though unlisted; whether a seed is silently accepted or honoured; what `usage` reports for reasoning tokens with thinking disabled; `length` versus context-overflow behaviour; the real 429 body and headers; whether any version or build marker is readable from a path, header, the listing's `name` or `system_fingerprint`, and whether it stays stable across repeated calls.

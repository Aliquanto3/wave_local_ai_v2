# Story: The ~0.5B class spans two families, or is published as a searched single-family ladder

**As** someone planning local AI on a 16 GB no-GPU office PC, where the smallest models are the ones that run
**I want** the ~0.5B class to hold a second family beside `Qwen3-0.6B`, scored on the same classification and translation items, or to be labelled a single-family ladder with every refused candidate's record behind the label
**So that** the smallest class compares models rather than one vendor's quant, and the first local rows from a family other than Qwen exist

Maps to: PRD AC "Given the published roster, each size class it publishes spans at least two model families, with dense and MoE both present where the class has both, and any single-family size class is labelled as such in the table"; PRD AC "Given the model roster, for each in-scope use case it includes at least one MoE candidate and at least one tiny dense candidate, run over the same items with results shown side by side, and each of them cites its entry in the versioned roster file"; Methodology 3, 4, 13; epic Boundaries "candidate coverage across the gap brief's families" (Granite 350M), "a recorded refusal for every candidate that does not enter", "the existing suites re-run on the dev machine as each addition's acceptance", "the roster version bump and the `docs/setup.md` download section per model added"; epic decisions "Where the class has them", "Unsupported architecture: defer by default", "EN/FR/DE capability is a claim, not a measurement"; epic success check 6.

Needs: a real local model run on the dev machine by an operator: GPU free, `SLM_MODELS_DIR` and `LLAMA_SERVER_PATH` set as for a run with `LLAMA_SERVER_PATH` on the b10537 `llama-server.exe`, nothing on port 8080. Gate downloads under 0.4 GB per candidate (1.12 GB if all three run), one load each, then both suites per entry. Architectures this story may load, in gate order: `granitehybrid`, `granite`, `lfm2` (three of the spike's eight). No API key; the build-upgrade tradeoff goes to the owner only on a `deferred` record (owner answer Q126 (a), 2026-10-03).

Current state (verified on `main` at `c68b23e`, 2026-10-03): the class holds one entry, `qwen3-0.6b-q8` (`Q8_0`, 596,049,920 total params, 639,446,688 bytes on disk), and its `size_classes` declaration in `aidd_docs/roster/models.json` (`roster_version` 4) is `single_family_ladder: false`, `moe_sought: false`, `moe_entry: null`, `moe_absent_reason: null`, so the README's composition block names two failures for it ("spans one family (qwen) without the single-family-ladder label", "has no MoE represented and no reason recorded"). `roster.KNOWN_FAMILIES` already holds `ibm` and `liquid`. `candidate_gate.run_gate` writes a pass record whose `entry` block carries `size_class` (`roster.size_class_for`), `bytes_on_disk`, `architecture.total_params`, `kind` and `expert_count` read off the GGUF, so an entry is a copy of that block. The candidate record file `candidate_gate.DEFAULT_RECORDS_PATH` (`aidd_docs/roster/candidate-records.jsonl`) does not exist yet; the first gate run creates it. `roster.SizeClassDeclaration` has four fields only: the ladder label is a boolean with no field naming refused candidates, so the refusals behind a label are read from the candidate record and named in the README's composition section.

## Acceptance

- The class's shortlist, as Q12 in `aidd_docs/tasks/2026_10/2026_10_01_autonomous-slicing/owner-questions.md` settles it, is Granite 350M and the smallest LFM2, plus any MoE GGUF the spike finds at this class, all restricted to the epic's families. Per owner answer Q107 (a), 2026-10-03, the LFM2 line is `LFM2.5-350M`; `LFM2.5-230M` stays out (a 0.23B model against `Qwen3-0.6B` would compare sizes, not families). The spike found no MoE GGUF at this class. The candidates go through the gate (order 4) one at a time, smallest download first, at the spike's pins: Granite 4.0 H 350M, `ibm-granite/granite-4.0-h-350m-GGUF@a864f823cce6e6048b5752e2816fe7a23987d790`, `granite-4.0-h-350m-Q8_0.gguf`, 366,195,616 bytes (`granitehybrid`); Granite 4.0 350M, `ibm-granite/granite-4.0-350m-GGUF@b8208a86a58427e1739265318028eb5895b74bf2`, `granite-4.0-350m-Q8_0.gguf`, 378,138,016 bytes (`granite`); LFM2.5-350M, `LiquidAI/LFM2.5-350M-GGUF@657e078c94084481950a2d555a941481f715536b`, `LFM2.5-350M-Q8_0.gguf`, 379,217,632 bytes (`lfm2`). Each candidate is taken at the quant of the class's Qwen entry (`Q8_0`) where its publisher ships it, otherwise at the nearest quant shipped, with the difference stated in the candidate record and on the README's composition section, so a family comparison is not read as a quant comparison. The search stops only when one non-Qwen entry has passed the gate and completed both suites (owner answer Q127 (a), 2026-10-03), which suffices: the class does not seek a third. A candidate that passes the gate but cannot complete both suites is withdrawn from `models.json` before merge, recorded with its reason in the story's evidence and the README's composition section, and the search continues with the next candidate. Every refusal on the way stays in the candidate record.
- Each passing candidate enters `aidd_docs/roster/models.json` from its pass record: a commit-sha revision, the sha256 read off the file, quant, architecture, `family` declared in the file, `size_class` (the band its total parameters fall in) with its two figures, total parameters and bytes on disk, licence block, language claim and thinking control. `roster_version` moves under the existing rule, and `docs/setup.md` gains its download section on the pattern step 3.1 set: `hf download <repo> <file> --revision <sha>`, then `Get-FileHash -Algorithm SHA256 ... .ToLower()`.
- The `lfm1.0` candidate (LFM2.5-350M) declares, and if it enters publishes, `client_commercial_use: false` on the spike's Assumption 3: section 5 of the LFM Open License v1.0 read against a user whose legal entity exceeds USD 10M annual revenue. The licence bans no publication of benchmark results, so the gate's licence step passes either way, and the README's composition section states that basis beside the entry.
- Each new entry runs the classification and translation suites to completion through the local chat path on the dev machine, launched with the flags its entry declares; where the declared offload does not fit, the value that launched is recorded rather than the one hoped for. Its rows carry its `roster_entry_id`, a `family` other than `qwen`, its `size_class`, and the `thinking_policy` its verified control applied. They join the published store as new rows; nothing published is edited.
- The class's declaration states two families, or carries the single-family-ladder label citing the refused candidates. Whether a MoE was sought at this class, and what the search found, is recorded with its reason when none is represented.
- The composition check (order 3) passes for this class, and the README's composition section is regenerated from it.
- Per owner answer Q126 (a), 2026-10-03, only a `deferred` record (step `load`, the server's "unknown model architecture" line) raises the one-time build-upgrade tradeoff to the owner; the story never changes the pinned build itself. A `refused` record at step `load` is named in the story's evidence with its verbatim line, and the search moves to the next candidate.
- Of the architectures this story may load (`granitehybrid`, `granite`, `lfm2`), the first gate run of each that reaches step `load` is also the GGUF spike's live load for that architecture under b10537 and closes the spike's question for it (owner answer Q108 (a), 2026-10-03): a pass's `observed` block carries the loaded build (`llama_cpp_build`), the `/props` chat template hash (`chat_template_hash`) and the verified thinking control (`thinking`). A pass, a `deferred` record, or a `refused` record whose `step` is `load` or later closes it, as a recorded outcome and not a failure of this story. A refusal at an earlier step (`revision`, `licence`, `disk`, `download`) does not: `observed.llama_cpp_build` is first written in the load step (`candidate_gate._step_load_and_thinking`) and the architecture is read off the downloaded file, so the architecture stays open until a candidate declaring it reaches load. Nor does a `load` refusal for a declared launch block that does not fit the file's kind, which the gate raises before `llama-server` starts. A refusal at step `thinking_control` carries the build and, once `/props` answered, the template hash, but no `observed.thinking`.
- Where an entry's suite rows contradict its EN/FR/DE claim, the claim stays and the README names the contradiction as a finding.

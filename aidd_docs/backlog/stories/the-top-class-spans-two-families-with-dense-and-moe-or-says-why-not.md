# Story: The top class spans two families with dense and MoE, or says why not

**As** a client decision-maker weighing the largest model a consumer machine can hold against a cloud model
**I want** the ~8B-and-up class to hold a second family beside the `Qwen3.6-35B-A3B` flagship, and a dense model beside the MoE ones, all scored on the same classification and translation items, or to say which of the two requirements it misses and why
**So that** the headline local model is compared against a rival, not only against its own vendor's smaller siblings, and a MoE win is read against a dense model of the same footprint class

Maps to: PRD AC "Given the published roster, each size class it publishes spans at least two model families, with dense and MoE both present where the class has both, and any single-family size class is labelled as such in the table"; PRD AC "Given the model roster, for each in-scope use case it includes at least one MoE candidate and at least one tiny dense candidate, run over the same items with results shown side by side, and each of them cites its entry in the versioned roster file"; Methodology 3, 4, 13; epic Boundaries "candidate coverage across the gap brief's families" (Gemma 4 including the 26B-A4B MoE), "a recorded refusal for every candidate that does not enter", "the existing suites re-run on the dev machine as each addition's acceptance", "the roster version bump and the `docs/setup.md` download section per model added"; epic decisions "Where the class has them", "Unsupported architecture: defer by default", "EN/FR/DE capability is a claim, not a measurement"; epic Dependencies "Whether the tower ... holds a Gemma-4-class 26B-A4B MoE at a usable quant", "Bench cost" (disk headroom checked before a download); epic success check 6.

Needs: a real local model run on the dev machine (a gate download of 6.4 GB for the dense Gemma 4 12B `IQ4_XS` and, only if the 12B does not pass, 13.6 GB for the Gemma 4 26B-A4B `UD-IQ4_XS` MoE, at the spike's pinned shas; one load each, CPU expert offload as the flagship runs applying to the 26B-A4B only; then both suites per entry; 6.4 GB of free disk under `SLM_MODELS_DIR` for the 12B, 19.97 GB if the 26B-A4B also runs). The run needs an operator: GPU free, `SLM_MODELS_DIR` and `LLAMA_SERVER_PATH` set as for a run with `LLAMA_SERVER_PATH` on the b10537 `llama-server.exe`, nothing on port 8080. Architecture this story may load: `gemma4` (one of the spike's eight, loaded by no other class story). No API key; the build-upgrade tradeoff goes to the owner only on a `deferred` record (owner answer Q126 (a), 2026-10-03).

Current state (verified on `main` at `c68b23e`, 2026-10-03): the class holds one entry, the MoE flagship `qwen3.6-35b-a3b-ud-iq4xs` (`UD-IQ4_XS`, 34,660,610,688 total params, 17,730,509,792 bytes on disk, `revision: "main"`, `validated_host.n_cpu_moe: 37`, no `family` key: it resolves to `qwen` through the in-code fallback of `roster.family_of`), so it has no second family and no dense model. Its `size_classes` declaration in `aidd_docs/roster/models.json` (`roster_version` 4) is `single_family_ladder: false`, `moe_sought: true`, `moe_entry: "qwen3.6-35b-a3b-ud-iq4xs"`, `moe_absent_reason: null`, and the README's composition block names one failure for it ("spans one family (qwen) without the single-family-ladder label"). `roster.KNOWN_FAMILIES` already holds `google`. `composition_check._class_failures` names a missing MoE without a reason but not a missing dense model, and `roster.SizeClassDeclaration` (four fields) has no field for a dense-absence reason, so a missing dense model's reason is read from the candidate record (`candidate_gate.DEFAULT_RECORDS_PATH`, `aidd_docs/roster/candidate-records.jsonl`, not yet created) and named in the README's composition section. `roster.validate_host_fit` refuses an `n_cpu_moe` above `architecture.expert_count`; the gate reads `expert_count` off the GGUF header key `<arch>.expert_count` (`candidate_gate.read_gguf_facts`), whereas the flagship's hand-written `expert_count: 40` is its layer count (its card and GGUF header say 256 experts), an open point of the 2026-10-01 run log that this story does not fix.

## Acceptance

- The class's shortlist, as Q12 in `aidd_docs/tasks/2026_10/2026_10_01_autonomous-slicing/owner-questions.md` settles it, is Gemma 4 26B-A4B (MoE) and Gemma 4 12B (dense); GPT-OSS 20B, Qwen3-Coder-30B-A3B and Mellum2-12B-A2.5B stay out, being outside the epic's families. The candidates go through the gate (order 4) one at a time, smallest download first, with free disk checked before each download, at the spike's pins: Gemma 4 12B it (dense), `unsloth/gemma-4-12b-it-GGUF@fc034cfff751157913579611efad8462ac1be606`, `gemma-4-12b-it-IQ4_XS.gguf`, 6,375,734,080 bytes (`gemma4`, `IQ4_XS` the nearest to `UD-IQ4_XS`, difference stated); Gemma 4 26B-A4B it (MoE), `unsloth/gemma-4-26B-A4B-it-GGUF@c099eb48e663fd284577b04978a94ffccb261841`, `gemma-4-26B-A4B-it-UD-IQ4_XS.gguf`, 13,597,177,568 bytes (`gemma4`). Both declare `{"chat_template_kwargs": {"enable_thinking": false}}`. Each candidate is taken at the quant of the class's Qwen entry (`UD-IQ4_XS`) where its publisher ships it, otherwise at the nearest quant shipped, with the difference stated in the candidate record and on the README's composition section, so a family comparison is not read as a quant comparison. The search stops only when one non-Qwen entry has passed the gate and completed both suites (owner answer Q127 (a), 2026-10-03; which suffices, the class does not seek a third) and both a dense and a MoE entry are represented, or when the shortlist is exhausted. A candidate that passes the gate but cannot complete both suites is withdrawn from `models.json` before merge, recorded with its reason in the story's evidence and the README's composition section, and the search continues with the next candidate. Per owner answer Q129 (a), 2026-10-03, Q12 (a)'s stop rule stays literal: the flagship already represents MoE, so if the Gemma 4 12B passes (gate and both suites) the 26B-A4B is not run, and the epic's closing record lists its dependency, whether the tower holds a Gemma-4-class 26B-A4B MoE at a usable quant, as untested (the epic asks it of the tower, not of this dev machine). Every refusal on the way stays in the candidate record.
- Each passing candidate enters `aidd_docs/roster/models.json` from its pass record: a commit-sha revision, the sha256 read off the file, quant, architecture (a MoE with its expert count and active-parameter figure), `family` declared in the file, `size_class` (the band its total parameters fall in) with its two figures, total parameters and bytes on disk, licence block, language claim and thinking control. `roster_version` moves under the existing rule, and `docs/setup.md` gains its download section on the pattern step 3.1 set: `hf download <repo> <file> --revision <sha>`, then `Get-FileHash -Algorithm SHA256 ... .ToLower()`.
- Each new entry runs the classification and translation suites to completion through the local chat path on the dev machine, launched with the flags its entry declares; a MoE entry declares its host expert offload and is refused by `validate_host_fit` if it exceeds its expert count, and where the declared offload does not fit, the value that launched is recorded rather than the one hoped for. Its rows carry its `roster_entry_id`, its `family`, its `size_class`, and the `thinking_policy` its verified control applied. They join the published store as new rows; nothing published is edited.
- Launch blocks: CPU expert offload applies to the 26B-A4B only. The 12B is dense and declares `validated_host.n_cpu_moe: null` and `load_mode: "auto"`, as the dense Qwen entries do. A `load` refusal for GPU memory is re-declared with a stepped-down `n_gpu_layers` and re-run before the candidate counts as not loading on the dev machine, the epic's practice from the dense ladder ("the model does not fit at -ngl 99 => -ngl is stepped down and the value that launched is recorded, not the value that was hoped for"); the first refusal stays in the candidate record.
- The class's declaration states two families, or carries the single-family-ladder label citing the refused candidates; and states dense and MoE both represented, or which is missing with the reason recorded (for example, a candidate that would not load on the dev machine is named with the load failure, not left blank). A missing dense model's reason lives in the prose of the README's composition section, citing the candidate-record line.
- The flagship keeps its `revision: "main"` pin and its byte-identical launch: the tech-debt row owns that fix, and this story does not retro-fit it.
- The composition check (order 3) passes for this class, and the README's composition section is regenerated from it.
- Per owner answer Q126 (a), 2026-10-03, only a `deferred` record (step `load`, the server's "unknown model architecture" line) raises the one-time build-upgrade tradeoff to the owner; the story never changes the pinned build itself. A `refused` record at step `load` is named in the story's evidence with its verbatim line, and the search moves to the next candidate, once a GPU-memory failure has been re-run under the launch-block rule above.
- The first gate run of `gemma4`, the one architecture this story may load, that reaches step `load` is also the GGUF spike's live load for that architecture under b10537 and closes the spike's question for it (owner answer Q108 (a), 2026-10-03): a pass's `observed` block carries the loaded build (`llama_cpp_build`), the `/props` chat template hash (`chat_template_hash`) and the verified thinking control (`thinking`). A pass, a `deferred` record, or a `refused` record whose `step` is `load` or later closes it, as a recorded outcome and not a failure of this story. A refusal at an earlier step (`revision`, `licence`, `disk`, `download`) does not: `observed.llama_cpp_build` is first written in the load step (`candidate_gate._step_load_and_thinking`) and the architecture is read off the downloaded file, so the architecture stays open until a candidate declaring it reaches load. Nor does a `load` refusal for a declared launch block that does not fit the file's kind, which the gate raises before `llama-server` starts. A refusal at step `thinking_control` carries the build and, once `/props` answered, the template hash, but no `observed.thinking`.
- Where an entry's suite rows contradict its EN/FR/DE claim, the claim stays and the README names the contradiction as a finding.

# Story: The ~4B class spans two families, or is published as a searched single-family ladder

**As** a consultant recommending a small dense model for a client's classification or translation work
**I want** the ~4B class to hold a second family beside `Qwen3-4B`, scored on the same classification and translation items, or to be labelled a single-family ladder with every refused candidate's record behind the label
**So that** the class the project's own candidate notes single out for classification ("a small dense classifier, 3-4B class") holds a second vendor beside Qwen, dense or MoE, and is a comparison of vendors, not a recommendation of the only one measured

Maps to: PRD AC "Given the published roster, each size class it publishes spans at least two model families, with dense and MoE both present where the class has both, and any single-family size class is labelled as such in the table"; PRD AC "Given the model roster, for each in-scope use case it includes at least one MoE candidate and at least one tiny dense candidate, run over the same items with results shown side by side, and each of them cites its entry in the versioned roster file"; PRD User Story "As a consultant, I want tiny dense models compared alongside MoE models on each use case"; Methodology 3, 4, 13; epic Boundaries "candidate coverage across the gap brief's families" (Ministral, Phi), "a recorded refusal for every candidate that does not enter", "the existing suites re-run on the dev machine as each addition's acceptance", "the roster version bump and the `docs/setup.md` download section per model added"; epic decisions "Where the class has them", "Unsupported architecture: defer by default", "EN/FR/DE capability is a claim, not a measurement"; epic Dependencies "Whether any MoE candidate exists in GGUF below the top class"; epic success check 6.

Needs: a real local model run on the dev machine by an operator: GPU free, `SLM_MODELS_DIR` and `LLAMA_SERVER_PATH` set as for a run with `LLAMA_SERVER_PATH` on the b10537 `llama-server.exe`, nothing on port 8080. Gate downloads of 2.0 to 2.5 GB per candidate at `Q4_K_M`, and 4.0 GB for Phi-tiny-MoE, whose only GGUF is `Q8_0` (10.65 GB if all four run), one load each, then both suites per entry. Architectures this story may load, in gate order: `granitemoe`, `mistral3`, `phi3`, `phimoe` (four of the spike's eight; no other class story may load `mistral3`, `phi3` or `phimoe`). No API key; the build-upgrade tradeoff goes to the owner only on a `deferred` record (owner answer Q126 (a), 2026-10-03).

Current state (verified on `main` at `c68b23e`, 2026-10-03): the class holds one entry, `qwen3-4b-q4km` (`Q4_K_M`, 4,022,468,096 total params, 2,497,280,256 bytes on disk), and its `size_classes` declaration in `aidd_docs/roster/models.json` (`roster_version` 4) is `single_family_ladder: false`, `moe_sought: false`, `moe_entry: null`, `moe_absent_reason: null`, so the README's composition block names two failures for it ("spans one family (qwen) without the single-family-ladder label", "has no MoE represented and no reason recorded"). `roster.KNOWN_FAMILIES` already holds `mistral`, `microsoft` and `ibm`. `candidate_gate.run_gate` writes a pass record whose `entry` block carries `size_class` (`roster.size_class_for`), `bytes_on_disk`, `architecture.total_params`, `kind` and `expert_count` read off the GGUF header (`<arch>.expert_count`, so a `granitemoe` or `phimoe` file enters as `moe`), so an entry is a copy of that block. The gate's licence step refuses a repo whose card declares no licence (`candidate_gate._step_licence`), and falls back to `README.md` when a repo carries no LICENSE file. `composition_check._class_failures` names a class whose MoE entry its declaration's `moe_entry` does not name, so a MoE that enters moves `moe_sought` and `moe_entry` with it. The candidate record file `candidate_gate.DEFAULT_RECORDS_PATH` (`aidd_docs/roster/candidate-records.jsonl`) does not exist yet. `roster.SizeClassDeclaration` has four fields only: the ladder label is a boolean with no field naming refused candidates, so the refusals behind a label are read from the candidate record and named in the README's composition section.

## Acceptance

- The class's shortlist, as Q12 in `aidd_docs/tasks/2026_10/2026_10_01_autonomous-slicing/owner-questions.md` settles it, is Ministral 3B and the Phi mini model, plus any MoE GGUF the spike finds at this class, all restricted to the epic's families. The candidates go through the gate (order 4) one at a time, smallest download first, at the spike's pins: Granite 3.1 3B-A800M (MoE), `bartowski/granite-3.1-3b-a800m-instruct-GGUF@be9a36f042806cb586bc65556c527079782b78e0`, `granite-3.1-3b-a800m-instruct-Q4_K_M.gguf`, 2,016,888,384 bytes (`granitemoe`); Ministral 3 3B Instruct 2512, `mistralai/Ministral-3-3B-Instruct-2512-GGUF@eb599d408350ea2bb60452cb86be7c7b2fc28227`, `Ministral-3-3B-Instruct-2512-Q4_K_M.gguf`, 2,147,023,008 bytes (`mistral3`); Phi-4-mini-instruct, `unsloth/Phi-4-mini-instruct-GGUF@78eb92a46fc37e6b524df991ed9aca9bc6aa7b80`, `Phi-4-mini-instruct-Q4_K_M.gguf`, 2,491,874,272 bytes (`phi3`); Phi-tiny-MoE-instruct (MoE), `tripathyShaswata/Phi-tiny-MoE-instruct-GGUF@873ccb08cd3380ee2c08573d45267fac9a6cc81b`, `Phi-tiny-MoE-instruct-Q8_0.gguf`, 3,999,171,104 bytes (`phimoe`, declared with `context_size: 4096`, its trained context). Each candidate is taken at the quant of the class's Qwen entry (`Q4_K_M`) where its publisher ships it, otherwise at the nearest quant shipped, with the difference stated in the candidate record and on the README's composition section, so a family comparison is not read as a quant comparison. The search stops only when one non-Qwen entry has passed the gate and completed both suites (owner answer Q127 (a), 2026-10-03; which suffices, the class does not seek a third) and the MoE question below is answered: one MoE has passed the gate and completed both suites, or every shortlisted MoE was refused, deferred or withdrawn. Once a non-Qwen family has passed, only the remaining MoE candidates are tried; further dense candidates are skipped. A candidate that passes the gate but cannot complete both suites is withdrawn from `models.json` before merge, recorded with its reason in the story's evidence and the README's composition section, and the search continues with the next candidate. Per owner answer Q128 (a), 2026-10-03, Q12 (a)'s stop rule stays literal: Granite 3.1 3B-A800M is non-Qwen and MoE at once, so its pass (gate and both suites) ends the search, and `mistral3`, `phi3` and `phimoe` are then not reached. Ministral and Phi stay the families Q12 names for the shortlist, not a requirement on the class. Every refusal on the way stays in the candidate record.
- Each passing candidate enters `aidd_docs/roster/models.json` from its pass record: a commit-sha revision, the sha256 read off the file, quant, architecture, `family` declared in the file, `size_class` (the band its total parameters fall in) with its two figures, total parameters and bytes on disk, licence block, language claim and thinking control. `roster_version` moves under the existing rule, and `docs/setup.md` gains its download section on the pattern step 3.1 set: `hf download <repo> <file> --revision <sha>`, then `Get-FileHash -Algorithm SHA256 ... .ToLower()`.
- Each new entry runs the classification and translation suites to completion through the local chat path on the dev machine, launched with the flags its entry declares; where the declared offload does not fit, the value that launched is recorded rather than the one hoped for. Its rows carry its `roster_entry_id`, a `family` other than `qwen`, its `size_class`, and the `thinking_policy` its verified control applied. They join the published store as new rows; nothing published is edited.
- Where the spike found a MoE GGUF at this class, it is taken through the gate like any candidate; where it found none, the class records that a MoE was sought and the search that came back empty, so "dense-only by nature" is distinguishable from "not looked at". If a MoE candidate is refused or deferred, the declaration records `moe_sought: true`, `moe_entry: null` and a `moe_absent_reason` naming the refusal record (its step and evidence), which `composition_check._class_failures` accepts in place of a MoE entry.
- The class's declaration states two families, or carries the single-family-ladder label citing the refused candidates.
- The composition check (order 3) passes for this class, and the README's composition section is regenerated from it.
- Per owner answer Q126 (a), 2026-10-03, only a `deferred` record (step `load`, the server's "unknown model architecture" line) raises the one-time build-upgrade tradeoff to the owner; the story never changes the pinned build itself. A `refused` record at step `load` is named in the story's evidence with its verbatim line, and the search moves to the next candidate.
- Of the architectures this story may load that no earlier class story has closed (`mistral3`, `phi3`, `phimoe`; `granitemoe` if order 6 did not close it), the first gate run of each that reaches step `load` is also the GGUF spike's live load for that architecture under b10537 and closes the spike's question for it (owner answer Q108 (a), 2026-10-03): a pass's `observed` block carries the loaded build (`llama_cpp_build`), the `/props` chat template hash (`chat_template_hash`) and the verified thinking control (`thinking`). A pass, a `deferred` record, or a `refused` record whose `step` is `load` or later closes it, as a recorded outcome and not a failure of this story. A refusal at an earlier step (`revision`, `licence`, `disk`, `download`) does not: `observed.llama_cpp_build` is first written in the load step (`candidate_gate._step_load_and_thinking`) and the architecture is read off the downloaded file, so the architecture stays open until a candidate declaring it reaches load. Nor does a `load` refusal for a declared launch block that does not fit the file's kind, which the gate raises before `llama-server` starts. A refusal at step `thinking_control` carries the build and, once `/props` answered, the template hash, but no `observed.thinking`.
- Where an entry's suite rows contradict its EN/FR/DE claim, the claim stays and the README names the contradiction as a finding.

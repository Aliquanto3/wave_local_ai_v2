## Decisions

| Decision | Why |
| -------- | --- |
| The scoring kind is read from the row shape, not from the suite or the caller: a row carrying the graded block (`metric_id` key) is `graded` and compares `item_score`; a row whose `correct` is a boolean is `binary` and compares `correct`; anything else has no scoring kind and is refused naming `scoring_kind` as absent. `TEST_BY_SCORING_KIND` maps `binary` to McNemar exact and `graded` to Wilcoxon signed-rank. | `architecture.md` already names the graded block's presence as the discriminator between the two score shapes; reading it off the rows means no caller can choose the test. A judged ordinal score is not routed yet: no judged row is in the bundle, and guessing its compared field would publish a test over an undeclared value. |
| `compared_field` keeps `verdict.py`'s meaning (the per-item value compared), and the configuration axis is a separate declared `compared_dimension` (`model` by default, or `prompt_variant`), each naming its row fields and its key fields. A comparison is a clean `test` only when the sides differ on a key field of the dimension and on nothing outside the dimension's fields; otherwise it is an `observation` naming its `confounds` and an `observation_reason`. | The acceptance uses `compared_field` in `verdict.py`'s sense (a `compared_field` mismatch is a refusal), yet also says a record whose sides "differ on more than the compared field" is an observation: that second use can only mean the compared configuration axis. PRD Methodology 24's family is "one suite crossed with one compared dimension", so the dimension is the declared half. |
| The `model` dimension covers `model_id`, `provider`, `roster_entry_id`, `roster_version`, `endpoint`, `prompt_template_id`, `prompt_template_hash`, `prompt_capture`, `sampling` and `fiche_hash`, keyed on `model_id`. | Methodology 1 and 2 record the call path and the sampling parameters per provider, so a local and a cloud subject differ on all of them by construction; counting each as a confound would make every local-versus-cloud comparison an observation. Stated limitation: inside a model comparison, a sampling change or a machine change carried only inside `fiche_hash` is not separable at the row level until the machine epic puts machine identity on the row (a `compute_mode` field already surfaces as a confound). |
| The differing-field set is computed over every row field except a declared exclusion list (bookkeeping such as `run_id`, `captured_at`, `commit_sha`; per-item fields; outcome and measurement fields such as scores, energy, cost and the reproduction `verdict`), comparing the set of values each side carries. A key present on one side only counts as differing; two nulls are equal there. | Computing from the rows rather than declaring a whitelist is what lets a field the contract does not yet hold (`compute_mode`) appear as a confound. The "null never matches" half of `verdict.py`'s convention is applied where the acceptance asks for it, to the four generation constraints and the metric identity: applied to every field it would make `prompt_template_hash: null` on two local rows a confound. |
| Refusal fields: `suite_id`, `suite_version`, `prompt_set_hash`, `suite_level`, the four generation constraints, `metric_id`/`metric_version`/`metric_params` on a graded row, `scoring_kind` and `compared_field`. The suite identity (`suite_id`, `suite_version`, `prompt_set_hash`), the four constraints and the metric triple refuse as `absent` when null or missing on either side; `suite_level`, `scoring_kind` and `compared_field` refuse when the sides disagree, and a field taking two values within one side refuses as `varies_within_side`. | Owner answer Q4 (a): two unknown values never count as a match, so the schema-7 rows refuse on `thinking_policy`. `suite_level` is held to "two different levels" as the acceptance words it, so two pre-schema-15 rows of one suite id and version are not refused for a level neither declares. The metric triple is the epic's wording; the acceptance's "identity and version" is a subset of it. Suite identity takes the absence rule too: Methodology 8's reasoning applies to an unknown suite as much as to an unknown constraint. |
| Wilcoxon conventions: Pratt's zero method; exact two-sided p from the full sign-flip distribution over the observed (tie-averaged) ranks when the non-zero count is at most 50, otherwise the normal approximation with Cureton's zero adjustment and the tie correction; no continuity correction. Rank-biserial is (W+ - W-) / (W+ + W-) over the non-zero ranks. | Pratt keeps an item both sides failed (an exact tie under Methodology 9) in the ranking instead of dropping it, which is what the acceptance asks. The sign-flip enumeration stays exact with ties and zeros (scipy's exact table does not), and a doubled-rank count table keeps it exact in integers. 50 is scipy's own exact threshold. |
| McNemar: exact two-sided binomial over the discordant pairs via `math.comb` in `Fraction`, statistic `min(b, c)`, odds ratio `c / b` (candidate-favoured over reference-favoured). | Reproduces the epic's 0.375 and 0.688 exactly, and the odds ratio's direction agrees with candidate minus reference. |
| Null reasons: `paired_n_below_minimum` (paired n of 0; both tests' minimum is one pair), `no_discordant_pairs`, `odds_ratio_empty_cell`, `all_differences_zero`. Verdict: `not comparable` for a refusal or `paired_n_below_minimum`; otherwise `distinguishable` when the adjusted p is at most alpha, else `not distinguishable` (a null p from sides that never disagree reads `not distinguishable`). Default alpha 0.05, declared on the record. An observation's verdict is `not comparable`, its p kept in `result` beside its `confounds`. | One value plus exactly one reason, on `agreement.py`'s shape. The three verdict strings are the acceptance's literals, reader-facing, so they keep their spaces rather than `verdict.py`'s snake case. The acceptance fixes the verdict to those three values and says an observation is never published as a clean test, so a reader of the verdict alone must not see a confounded pair as `distinguishable`; a fourth value would contradict the acceptance. The p stays in `result`, where a significant one reads as "the bug signal it is" (epic). |
| One invocation compares one declared pair and writes one family record of one member to `aidd_docs/results/comparisons/<name>.json`; its `family_id` is the sha256 of the record's canonical content without it (`rows_source` normalised first: working-directory-relative POSIX path when under it, else the resolved absolute path, so two spellings of one file give one id), no timestamp is written, and an existing file is rewritten only when byte-identical (otherwise refused). | Re-running over the published bundle returns identical bytes, which is the reproducibility check; write-once matches `suite_snapshot.py`'s discipline. Multi-member families and supersession are order 3. |
| scipy is added to the `dev` dependency group only. | The epic's decision: statistics on the standard library at runtime, scipy as an independent oracle in tests. |

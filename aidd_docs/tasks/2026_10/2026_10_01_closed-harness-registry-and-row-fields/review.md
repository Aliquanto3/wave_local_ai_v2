### Plan decisions judged

- Overhead as one `{tokens, null_reason}` object => sound. It keeps "a value, or null with its reason" inside one field. The gate refuses a negative count, a bool, a measured count that also carries a reason, and a null without a known reason. Cloud rows get `item_prompt_not_counted`, which is honest because no tokenizer count exists. A negative subtraction becomes `unmeasurable`, a sensible extension of Q33 (a): the engine did not receive the item as rendered. `direct` measured at 0 => matches the live proof that `/tokenize` (add_special) equals `usage.prompt_tokens`, including when the cache serves part of the prompt.
- `comparison.py` excludes the overhead from the differing set and compares the id => correct: the overhead is an outcome, the id is configuration (`test_a_harness_overhead_is_a_measurement_and_never_a_confound`, `test_two_models_under_two_harnesses_are_confounded_by_the_harness`). Comparing `harness_version` is the questionable part (non-blocking 1).
- Schema "20": rows below "20" are exempt and never back-filled (`test_an_earlier_version_row_without_the_harness_fields_still_validates`). The committed `quality-reference.jsonl` (80 rows) and `runtime-reference.jsonl` (2 rows) are schema "7". They already fail the current gate on earlier fields (item_*, retry_budget, ...), so that failure predates this task. A scratch `validate_row` run confirmed that none of their missing-field lists names a harness field. The task adds no new failure, and the existing store tests pass.

### Non-blocking findings

1. `harness.py:42` / `comparison.py:278`: `direct`'s version is the `requests` version. That satisfies "read from the installed package", and no truer package exists for "plain client calls". But `harness_version` stays in the comparison's differing set, so a routine `requests` bump (one the dependency audit may force) turns every later model or leader-set pair that spans the bump into an observation. The reason would have nothing to do with what the engine receives, which is the project's own code (`commit_sha`, excluded as bookkeeping). Fix: exclude `harness_version` from the differing set when both sides are `direct`, or record the question for the harness-comparison story, which owns the harness dimension. No schema-20 row has been published yet, so nothing is affected today.
2. `tests/test_harness.py:69`: the "tool definitions" test is arithmetic only. No writer passes `tools` yet, so keeping the render and the answer consistent depends on the caller. Suggestion: when the tool-calling story lands, take the item's tools once and send them to both `/apply-template` and the chat call, with one stubbed end-to-end test asserting the overhead.
3. Earlier gap from commit 11b9b2b (composition-check story), not this task's code: `comparison.DIMENSIONS["model"].fields` (`comparison.py:298-323`) lacks `family` and `size_class`. A scratch check of two schema-19+ rows, `model-a`/qwen/~1B against `model-b`/gemma/~4B, returned `comparison_kind observation`, `confounds ['family', 'size_class']`. A clean model test therefore degrades to an observation, and `leader_set.py:569` uses the same path. Fix: add `family` and `size_class` to the `model` dimension's fields, as is already done for `subject_egress` (each is a function of the model), and add a test.
4. `row_contract._validate_harness` returns early unless all three fields are present. A row below "20" that carries only some of them is not shape-checked. It cannot happen through the writers.

## Decisions

| Decision                                                                                                                 | Why                                                                                                                                                                                                                                                     |
| --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The builder stage copies the whole extracted `llama-b10537/` directory into the runtime stage (e.g. `/opt/llama-cpp/`), not one isolated `llama-server` file | The asset is a dynamically-linked build; `llama-server` alone would fail at container start with missing `.so` errors. Copying the directory is still "only the binary" in spirit — no build toolchain, no source archive, no dev headers cross the stage boundary, just the shipped runtime the release actually is. |
| `uv sync --locked --no-dev --no-editable` in the builder, and the runtime stage copies only `.venv/` (no `src/`, no `pyproject.toml`, no `uv.lock`)                     | `--no-editable` makes the venv self-contained (a real installed package, not a path reference back to source) — the only way the story's "copy only... the synced venv" is achievable without also shipping the repository into the image.              |
| `compose.yaml` overrides `SLM_MODELS_DIR` and `LLAMA_SERVER_PATH` in `environment:`, after `env_file: .env` supplies the rest                                          | The developer's own `.env` holds host-native paths (a Windows drive letter, a host-only binary path) that mean nothing inside the container's filesystem; `env_file` alone would make `load_settings()`'s existence check fail on every run. `environment:` in compose takes precedence over `env_file:` per Compose's own merge order, so the two host-specific keys get container-correct values while every other key (`MISTRAL_API_KEY`, `GOOGLE_API_KEY`) still flows from the host's `.env` untouched. |
| The `quality` service overrides `entrypoint:` to `wave-local-ai-v2-quality` instead of relying on `command:`                                                          | The Dockerfile's `ENTRYPOINT` is fixed to the `wave-local-ai-v2` console script per the task brief; Compose `command:` only appends arguments to an entrypoint, it cannot swap the executable. `entrypoint:` at the service level is what Compose exposes for exactly this override, and it needs no image variant or extra build. |
| CI's `required` job depends on `[test, build]` and treats a `skipped` `build` result as passing, not just `success`                                                   | `build` only runs `if: github.event_name == 'pull_request'`; on a push to `main` (post-merge) it is legitimately skipped, and `required` must not go red for a job that was never supposed to run on that trigger. |
| `publish` is a separate job gated on `startsWith(github.ref, 'refs/tags/v')`, outside the `required` job's dependency graph entirely                                  | `main`'s branch-protection ruleset only evaluates `required` on PRs targeting `main`; a tag push is a different ref and different event, never passes through that ruleset, and gating `required` on `publish` would deadlock every PR (which never produces a tag). |
| `packages: write` is granted only at the `publish` job's `permissions:`, not at the workflow's top-level `permissions:`                                               | The workflow's top-level `permissions: contents: read` (already in `ci.yml`) stays the least-privilege default for `test` and `build`; only the one job that actually pushes to GHCR needs the elevated scope, matching the story's explicit "scoped to that job only". |

## Risks

- The GitHub-computed asset `digest` is not a checksum llama.cpp itself publishes or signs — it is GitHub's own re-hash of what it received on upload. It is still the only per-asset checksum that exists for this release (verified: no `SHASUMS`-style file among the release assets), and it was cross-checked locally against the actual downloaded bytes, but this is a materially weaker trust chain than the model file's checksum in `docs/setup.md` §3, which is documented as a limitation in phase 4, not silently treated as equivalent.
- A future `uv` minor release could change `--no-editable`'s behavior or default; pinning the builder's `uv` to `0.11.7` (the version `pyproject.toml`'s `uv_build` upper-bounds against) keeps the build stage's `uv sync` behavior matched to the same `uv` the lockfile was produced with.
- Docker is available locally for the executor; phase 1-2 acceptance criteria require an actual local `docker build` and `docker compose up` run against the real b10537 CPU asset and a real `uv sync`, not just a read of the file — a network-dependent build stage (the asset fetch) can still fail in a restricted CI runner even after passing locally, which is why phase 3 keeps its own independent build-job acceptance criterion.

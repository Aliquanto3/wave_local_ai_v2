# Codebase Audit: performance

The timed metrics are safe (server-reported), but the energy windows around them fold in idle cooldown and model-load time, which distorts every energy, emissions and cost-per-token figure across models and machines.

- **Date**: 2026_09_22
- **Scope**: full codebase (`src/wave_local_ai_v2/`, `frontend/src/`), ranked by the publication objective (defensible numbers, reproducible on three machines)
- **Health**: fair
- **Findings**: 1 critical, 2 warning, 4 minor

Health: `good` = no critical findings; `fair` = critical findings exist but are isolated and addressable; `poor` = systemic or widespread critical findings.

## Findings

| Sev | Category    | Location | Issue | Suggested fix | Effort |
| --- | ----------- | -------- | ----- | ------------- | ------ |
| 🔴  | performance | `src/wave_local_ai_v2/__init__.py:351`, `src/wave_local_ai_v2/repetitions.py:126-127` | The CodeCarbon tracker wraps `_run_counted`, so the `(N-1) x cooldown_s` idle sleeps are inside the energy window. Measured on the live store: the idle share of the window is 0.43 for the 35B MoE, 0.47 for 4B, 0.84 for 1.7B and 0.89 for 0.6B (`(repetitions_n-1)*cooldown_s` over that plus `wall_clock_s`). CPU (`estimated_tdp`) and RAM (`estimated_constant`) energy grow with elapsed time, so for small or fast models `energy_kwh`, `emissions_kg`, `cost_total` and `cost_per_million_tokens` mostly measure 40 s of idle. The fixed idle term penalises faster models and faster machines, which inverts the dense-vs-MoE energy comparison and breaks comparisons across the three machines. The row does declare it (`aggregation.energy_kwh = "total_over_counted_repetitions_including_cooldowns"`), but the per-token cost built from it does not, and no view shows the label (see ui.md). | Measure the active window only: start and stop the tracker around each `send()` and sum the results, or sample an idle baseline during one cooldown and publish active and idle energy as separate fields. Build `cost_per_million_tokens` and emissions from active energy, and bump the schema version. | M |
| 🟡  | performance | `src/wave_local_ai_v2/quality_cli.py:460-463`, `src/wave_local_ai_v2/quality_cli.py:763-773` | The local quality energy window spans the whole `_run_local_suite`: the llama-server launch (loading the 17.7 GB MoE from disk), the readiness wait, an extra `/apply-template` round-trip per item, and teardown. Unlike runtime rows, quality rows carry no `aggregation` label stating this span. Live example: the 35B classification batch records 1.4 to 1.6 Wh for 240 output tokens, which is mostly model load. Disk speed differs between the three machines, so local quality energy and cost are not comparable across hosts, or against the cloud Scope-3 rows beside them. | Start the tracker after readiness, render every prompt before the tracker starts (it is only needed for publication), stop the tracker before teardown, and write a window label on the row. | M |
| 🟡  | performance | `src/wave_local_ai_v2/read_model.py:971-976` | `comparison_view` builds a full `_quality_entry` for every compared cell, and each one reads a fiche JSON (`resolve_fiche`) and a suite snapshot (`resolve_suite_definition`) from disk. The cell then keeps only `COMPARISON_CELL_FIELDS` (`read_model.py:365`), which has neither. Measured on the 591-row store: 225 fiche reads and 225 snapshot reads per `GET /api/comparisons`, 249 ms against 17 ms for `runs_view`. The disk I/O grows with cells, not with suites. This is in-flight uncommitted code on `feat/dense-moe-view`. | Resolve only the fields a cell needs (`resolve_fields(row, COMPARISON_CELL_FIELDS ...)` plus `score_shape_of`), or memoise `resolve_fiche`/`resolve_suite_definition` per request, keyed on hash and (suite_id, version). | S |
| 🟢  | performance | `src/wave_local_ai_v2/read_model.py:663-670` | `quality_view` re-reads the same fiche and suite snapshot for every row (42 of each for a 42-row run), and repeats the resolved fiche, roster entry and judge block on every entry. The payload is 266 KiB for 42 rows: 29% (78 KiB) is the judge block, where every field is an identical absence, and 11% is the duplicated fiche. | Use a per-request dict cache for pointer resolution. Optionally, hoist run-invariant blocks (fiche, suite definition) to the view level. | S |
| 🟢  | performance | `src/wave_local_ai_v2/repetitions.py:166-168`, `src/wave_local_ai_v2/gpu.py:20`, `src/wave_local_ai_v2/machine_state.py:59` | Each repetition opens and closes two NVML sessions (`nvmlInit`/`nvmlShutdown`) after the completion returns. This happens outside the timed metrics (server-reported), but it delays the `gpu_draw_w` sample into post-decode near-idle power (live: 40 W on the 35B, 94 W on 1.7B), so the peak-labelled power figure carries little information. | Open one NVML session per repetition set and read GPU stats and machine state from the same handle. Or drop `gpu_draw_w` as a peak in favour of the NVML energy counter CodeCarbon already uses (`nvmlDeviceGetTotalEnergyConsumption`). | S |
| 🟢  | performance | `src/wave_local_ai_v2/__init__.py:301` | `requests.post` without a `Session` opens a new TCP connection per repetition inside the `wall_clock_s` window. This is negligible on loopback, and `wall_clock_s` is a declared total, not a headline. | Reuse one `requests.Session` for the repetition set. | S |
| 🟢  | performance | `src/wave_local_ai_v2/service.py:176-190`, `src/wave_local_ai_v2/read_model.py:532-583` | `/api/runs` is unpaginated and grows linearly with runs (today 23 quality runs, 32 KiB, 17 ms). This is not a problem at pitch scale. | No action until the store reaches roughly 1k runs, then add `limit`/`cursor`. | S |

Not new (deduped): `tech-debt.md` row "`service.py:136` `loaded_roster()` re-parses the roster... 591-row quality store is re-parsed per call" covers the whole-store re-read per request. It measures at 16 ms per parse of the 1.9 MB store, so there is no case for escalating it.

Checked and clean. Every published timing (`ttft_ms`, `prompt_tok_per_s`, `gen_tok_per_s`) comes from llama-server's own `timings` block (`timings.py:70-86`), so client-side work cannot contaminate it: NVML reads, JSON parsing, `append_row`, the verdict computation after the server context exits (`__init__.py:446-453`). The local path has no retry (`local_client.py:34`), and cloud retries never touch local timing. The frontend bundle is 216 KiB JS / 66 KiB gzip with React as its only runtime dependency, and no hot render path needs memoisation at current payload sizes.

## Top actions

1. Restrict the runtime energy window to active requests, or publish idle separately, and derive emissions and cost-per-token from active energy (resolves the 🔴 row). Hand off to `aidd-dev:01-plan`: it changes the row schema and invalidates the energy columns of every published runtime row.
2. Narrow the local quality energy window to post-readiness generation and label it on the row (resolves 🟡 `quality_cli.py:460`). Plan it together with action 1 so the two windows share one declared definition.
3. Stop the comparison route resolving fiches and snapshots it discards, and add a per-request pointer cache for `quality_view` (resolves 🟡 `read_model.py:971` and 🟢 `read_model.py:663`). Hand off to `aidd-dev:07-refactor` (performance axis), ideally before `feat/dense-moe-view` merges.

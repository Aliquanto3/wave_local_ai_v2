## Decisions

| Decision | Why |
| -------- | --- |
| No field named `leader_set_member` (or any leader-set concept) exists anywhere in `row_contract.py`, a store, or the reference bundle today — confirmed by grep. `read_model.py` reads it as a plain row field via the existing `resolve_field` machinery (`Absent(ABSENT_PREDATES_SCHEMA, …)` on every row today), never a new absence reason and never a stub written into `row_contract.py`. | The story is explicit: "Nothing in the repo produces a leader set today (the stats epic records its derivation as unowned)." `a-score-is-published-with-its-interval-a-difference-with-its-test.md`'s own Dependencies table names the leader set "assumption, **unowned**." Inventing a field in `row_contract.py` for a derivation this story does not own would be exactly the fabrication `CoverageRecord.tsx`'s own precedent (same epic family) already ruled out for the coverage record. Reusing `resolve_field`'s existing three-reason contract is the same trick that record used, applied to a row field instead of a whole construct. |
| `PROVIDER_LOCAL = "local"` is declared as a `read_model.py`-local constant (a one-line literal, citing `judge_probe.PROVIDER_LOCAL` in a comment), not imported from `judge_probe`. | `judge_probe.py` is a probe-execution module pulling in the Mistral/Google client stacks — importing it into the read-only service module for one string constant would contradict `read_model.py`'s own module docstring rule ("only read paths are imported, by name") and its "no HTTP client reachable from a read request" posture. `_comparison_columns` already establishes the pattern of reading `provider` as a plain row field with no shared enum. |
| Use cases are grouped by the quality row's `task_suite` field (e.g. `"classification"`), not `suite_id` (e.g. `"classification-support-routing"`). One card per distinct `task_suite` value present in the quality store. | Confirmed against `aidd_docs/results/quality-reference.jsonl`: `task_suite` is the human use-case name the PRD's nine-use-case list and the `no-use-case-is-silently-absent` epic both speak in; `suite_id`/`suite_version` is the specific suite artifact `comparison_view` already groups by for a different purpose (side-by-side item comparison, not use-case identity). |
| **The view-boundary carve-out**, read exactly as the epic states it: Success Evidence's fifth check is "Quality and runtime never arrive together — verified by there being no endpoint that returns both, not by a convention about how the pages are laid out." No server response ever carries both stores' data (two routes, each reading exactly one store); the composition of a runtime/energy headline onto a quality leader happens in the browser, after two independent fetches, inside `views/overview/OverviewView.tsx` — the one file in the new tree that is allowed to know both stores exist, because it is neither "the quality panel," "the runtime-and-energy panel," nor "the card shell," the three pieces the story's boundary bullet names and `boundary.test.ts` is extended to check. `OverviewView` fetches `/api/overview/quality` once to build the suite list, the per-suite leader `roster_entry_id`s (bare strings, not typed quality entries) and the single coverage-absence banner; it passes a `suite: string` and a `leaderRosterEntryIds: string[]` — both primitives, no quality or runtime type — down through `OverviewCard` (the shell) to `overview/quality/QualityPanel` (self-fetches `/api/overview/quality` again, filtered to its `suite`) and `overview/runtime/RuntimeEnergyPanel` (self-fetches `/api/overview/runtime` once, looked up by the `leaderRosterEntryIds` it was handed). | This is "the narrowest reading of the epic's 'no response that returns both' rule under which the PRD's card can exist," per the story's own line, and the story explicitly asks for the epic's Boundaries to be amended to say so. The alternative — a card shell that receives typed quality and runtime entries as props — would make the shell import both view models, exactly what `boundary.test.ts`'s existing quality/runtime scan (extended the same way to `overview/quality` and `overview/runtime`) is built to fail. Duplicate fetching of the small `/api/overview/quality` response (once in `OverviewView`, again per-card in `QualityPanel`) is accepted: every existing screen (`QualityView`, `RuntimeView`, `EnergyView`) already self-fetches independently with no shared cache, and the overview's suite count (≤9 per the PRD) keeps this cheap. |
| The runtime+energy headline route (`/api/overview/runtime`) is **store-wide, keyed by `roster_entry_id`**, not suite-scoped — mirroring `runs_view`'s own documented fact that "a runtime row carries no suite dimension." It returns the latest (`captured_at`-sorted, same tie-break as `_comparison_columns`) runtime headline per `roster_entry_id` present in the runtime store, for every `roster_entry_id`, not filtered to any leader. | The runtime store has no `task_suite`/`suite_id` field to filter by, and computing "which entries are leaders" is quality-store knowledge this route must not read (previous decision). Returning every `roster_entry_id`'s headline and letting the browser look up the one(s) named by `leaderRosterEntryIds` keeps the route honestly scoped to one store while still answering the story's requirement. |
| The overview's coverage-absence banner renders **once, at the `OverviewView` level**, not once per card — a new `overview/CoverageAbsence.tsx`, structurally identical to `views/quality/CoverageRecord.tsx` (same `DeclaredAbsenceLabel` reuse, same `no-use-case-is-silently-absent` reason) but not the same component instance. | The story's AC says the absence is stated "once," not once per card — a different placement than `CoverageRecord`'s per-quality-run rendering. Because no coverage record exists, the overview also renders no out-of-scope cards and guesses no use case beyond the `task_suite` values the quality store actually carries — reusing `CoverageRecord.tsx` unmodified (per-run scoped, always rendered) would be the wrong cardinality for the overview screen. |
| The overview's response and view-model types live in `overview/quality/types.ts` and `overview/runtime/types.ts` (their own directories), never in the shared `api/types.ts`, matching the sibling story's own established Decision for `quality/`, `runtime/` and `energy/`. | `api/types.ts` holds only the identity/absence primitives (`Absent`, `Maybe`, `RosterEntry`) and `RunsView` every screen already shares; the prior story's plan already reasoned that putting a screen-specific view model there would make `api/types.ts` itself an import every screen touches, silently defeating the boundary test. This plan follows that precedent rather than the story's literal "Code it changes" line naming `api/types.ts`, since the precedent is stronger evidence of the codebase's own convention than the story's file list, which describes the target shape rather than a diff (the sibling story's plan made the same call for the same reason). |
| The overview becomes `App.tsx`'s initial `Selection` state (`{ status: 'overview' }`), replacing `{ status: 'runs' }` as the default; the runs list is reached by one button click from the overview (`onClick={() => setSelection({ status: 'runs' })}`), same state-machine style already in use. | No router is installed (confirmed unchanged since the sibling story's own Decision); `App.tsx` already holds a hand-rolled `Selection` union and swapping which variant is the initial value is the smallest change that satisfies "opening the service's root shows the overview; the runs list stays one navigation step away." |
| The two new routes (`/api/overview/quality`, `/api/overview/runtime`) sit on the existing gated `api` router in `service.py`, inheriting the same `Depends(key_gate)` every other `/api/*` route already carries — no new dependency wiring. | `service.py`'s `api = APIRouter(prefix="/api", dependencies=[Depends(key_gate)])` already gates every route added under it; adding two more `@api.get(...)` functions is the same pattern `get_runs`/`get_comparisons` already use, and the story's own "behind the same key gate as the four views, answer 405 to every other method" AC is satisfied by construction, not by new code. |

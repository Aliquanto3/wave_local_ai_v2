# Plan: The local quality path answers through the model's own chat template

## What the defect actually asks for

The defect's Verification is four observable facts on one future row: a `prompt_template_id` other than `none`, a non-null `prompt_template_hash`, a `prompt` holding the chat-rendered string rather than the bare item text, and a suite version above the one the superseded rows carry. Nothing else in it is a requirement. The phases below are ordered so each of those four becomes true exactly once, and so no row is written between the code change and the version bump that could be confused with a published one.

`prompt_provenance.is_consistent` already refuses a templated endpoint that declares `template_id: none`. That rule has had no producer since it landed: every local row took the one exemption in `RAW_ENDPOINTS`. This increment is the producer.

## What phase 1's live probe changed about this plan

The first revision of this plan assumed the endpoint switch was the whole remedy. It is not, and `evidence.md` in this folder holds the transcript. On `Qwen3-0.6B` at the classification suite's 32-token cap, the chat endpoint returns `content: ""` with the entire cap spent in `reasoning_content` — a suite score of 0.00, worse than the 0.45 the untemplated path published and misleading for a second reason. A chat-tuned model asked through its own template does not answer; it thinks first, and a 32-token cap ends before the answer starts.

Four request-level controls were probed. `chat_template_kwargs: {"enable_thinking": false}` and `reasoning_effort: "none"` both yield `content: "technical"`, `finish_reason: "stop"`, two tokens. `reasoning_budget: 0` does nothing. `reasoning_format: "none"` only moves `<think>` back into `content`. `/apply-template` honours the same `chat_template_kwargs` — undocumented, verified live — so the stored prompt can be the exact string the chat call rendered.

The plan below therefore carries a second moving part the first revision did not have: **the suite declares a thinking policy**, and every row records it.

| D4 | The instruction names `judge_probe.py` as context, not as scope | `judge_probe._generate_local_outputs` migrates too, through the same shared client | It carries a verbatim third copy of the raw POST (`tech-debt.md`, 2026-09-06 `judged-probe-both-paths-three-languages`) and therefore the identical defect. ## Assumptions

- **The sampling pins survive the endpoint change unchanged.** Settled live, not assumed: b10537's chat endpoint accepts all five `LOCAL_SAMPLING` keys and two identically-sampled requests returned byte-identical content, so `top_k: 0` carries its `/completion` meaning here and the `sampling` block on every row is unchanged.
- **`--jinja` is already on every launch.** All four roster entries set `jinja: true` (`aidd_docs/roster/models.json`) and `server.build_flags:89-90` emits it. No flag, roster or launch change is needed, and `server.py` is not touched: the byte-identical-launch tests stay green by construction.
- **A re-run is one invocation per entry per suite with `QUALITY_PROVIDERS=local`.** Eight local batches, no cloud quota. The `gemini-3.5-flash-lite` comparator is cited from the rows already on disk, as the dense increment did — except that those rows sit at the old suite version, which phase 4 has to state rather than paper over (see Risks).

| `https://raw.githubusercontent.com/ggml-org/llama.cpp/b10537/tools/server/README.md` | `POST /apply-template` takes `messages` (same shape as the chat endpoint) and returns the rendered string under a `prompt` key. `POST /v1/chat/completions` accepts `seed`, `temperature`, `top_k`, `top_p`, `presence_penalty` and `max_tokens`, returns `choices[].message.content`, `choices[].finish_reason` (`stop` / `length` / `tool_calls`) and `usage.{prompt_tokens,completion_tokens,total_tokens}`, and echoes the rendered prompt nowhere. `GET /props` returns `chat_template`, the model's own Jinja template string, alongside `model_path` and `build_info`. `/completion` reports `stop_type` with values `none` / `eos` / `limit` / `word`. | The installed `b10537-bf0040e15` binary, probed live (`evidence.md`) | Every README claim above confirmed, with one correction and one measurement the document does not carry. **Correction:** `/apply-template` also honours `chat_template_kwargs`, which the README's option list omits — the rendered prompt gains a `<think>\n\n</think>\n\n` prefill under `enable_thinking: false`, so the row's stored string can match the chat call's exactly. **Measurement:** of the four reasoning controls, only `chat_template_kwargs: {"enable_thinking": false}` and `reasoning_effort: "none"` actually suppress thinking on this template; `reasoning_budget: 0` has no effect as a request parameter and `reasoning_format: "none"` merely stops the envelope being parsed out of `content`. |

## Decisions

| Decision | Why |
| -------- | --- |
| One new module, `local_client.py`, beside `mistral_client.py` and `google_client.py` | The raw POST already exists three times (`quality_cli`, `judge_probe`, `__init__`), which `tech-debt.md` files as open debt. Adding a fourth copy for the chat call would make it four. One module with the same shape as the two cloud clients — content, truncation flag, token counts, the endpoint it called — lets `quality_cli._run_local_suite` and `judge_probe._generate_local_outputs` read the same as the cloud paths they sit beside. The runtime harness's own copy in `__init__.py` is deliberately left alone. |
| The runtime benchmark keeps posting to `/completion`, untouched | Its number is raw generation throughput against a fixed prompt reproduced from `context_input/baseline_qwen36.md`; a chat template would change the token count it measures and break the reproduction verdict against every published runtime row. The two paths measuring different things is the point, and each row already names its own endpoint. |
| `prompt_template_id` is one fixed constant, `prompt_template_hash` varies per model | The hash is `sha256` of the exact `chat_template` string `/props` reports, so it identifies the template that actually rendered the prompt and moves when the model does. A per-entry id would restate `roster_entry_id`, which every row already carries. This mirrors the two cloud constants, where the id names the wrapper and the hash pins its content. |
| The rendered prompt is fetched from `/apply-template` per item, and the row says `reconstructed` | Same server, same loaded template, same `messages` — but a different request from the one that generated the answer. `reconstructed` is what that is. See D2. |
| The suite declares `thinking_policy`, `disabled` or `allowed`, and both shipped suites declare `disabled` | The switch decides whether a number exists at all, so it cannot live in the CLI. It belongs where `max_output_tokens`, `stop_sequences` and `context_length` already live — Methodology 3's "belong to the suite definition, are identical across every model compared on an item, and are recorded per row" — because it is the same kind of constraint: what the model is permitted to spend its cap on. `disabled` for both shipped suites keeps the published 32/128 caps meaningful; a future suite that wants deliberation declares `allowed` and sizes its cap for it, which is a suite's decision to state rather than a harness default to inherit. |
| `thinking_policy` is recorded on **every** quality row, cloud rows included, and is enforced only where the provider offers a switch | It is the suite's declared policy, not a report of what each provider did — the same status `stop_sequences` already has, which every row publishes while it is sent to no provider today. The distinction is stated on the contract rather than left to a reader: `thinking_policy` says what the suite asked for, and the call-path fields say how each provider was actually addressed. Recording it only on local rows would make the field mean two things depending on where you read it. |
| `row_contract.SCHEMA_VERSION` moves `"10"` -> `"11"` | A required field is added to the quality row. This is the same shape as `"8"` (`retries` / `resumed`, quality rows only, runtime untouched). The published bundle stays at `"7"` and `test_reference_bundle.py`'s "never ahead of the code" assertion keeps holding. |
| Both suite versions bump: classification `"2"` -> `"3"`, translation `"1"` -> `"2"` | `verdict.select_quality_references` keys on `task_suite`/`model_id`/`suite_version`/`seed`, so the bump is what makes the new rows structurally incomparable to the untemplated ones instead of quietly reproducing against them. `prompt_set_hash` does **not** move — no prompt is edited — so the pair (`suite_version`, `prompt_template_id`) is what separates the two generations, and phase 3 states that on the suite modules rather than leaving a reader to infer it from a version that changed with no hash change behind it. |
| Suite snapshots become `<suite_id>@<suite_version>.json`, superseded files kept | The same discipline `runtime-reference.schema-1.jsonl` already follows: a reader chasing an old citation still finds the definition that row was produced against. See D5. |

## Risks

- **The thinking switch is verified on one model of one generation.** `Qwen3-0.6B` answers under `enable_thinking: false`. The 1.7B and 4B share its template family, but `Qwen3.6-35B-A3B` is a different generation with a different template, and it is the one entry that already obeys on the raw path — its `chat_template_caps` may not accept the argument at all, in which case its rows would carry `thinking_policy: disabled` while nothing enforced it. Phase 1 probes the flagship once before the matrix is paid for, and a failure there is a finding that changes phase 4's shape, not something to discover mid-run.
- **The 128-token translation cap may not need the switch.** Four times the classification cap may be enough for a thinking model to reach an answer, which would make `disabled` a policy that changes translation scores for no reason. Phase 1 probes one translation item both ways and records the pair, so the policy applies to that suite on evidence rather than by symmetry with the other one.
- **`disabled` measures a narrower model than the vendor ships.** A Qwen3 with thinking off is not the Qwen3 the card benchmarks, and a reader could take a routing score as the model's ceiling. Mitigated by the field itself: every row says which policy produced it, and phase 4's record states that a thinking-allowed run is a different, unpublished measurement — the option the defect now names as deferred on cost.
- **The empty `<think>\n\n</think>` prefill still costs chrF precision.** Disabling thinking does not remove the envelope from the rendered prompt; it prefills an empty one. Whether it also lands in `content` on the translation suite is what phase 1's translation probe answers. If it does, the ~15-character penalty the `translation-suite-live-run` tech-debt row records survives this increment, and that row stays open rather than being quietly closed by a change that did not fix it.
- **The re-run may not rescue the dense models.** The defect claims only that the published numbers measure the wrong thing, never that the models are good. If a 0.6B still scores 0.45 under its own chat template, that is the answer the comparison was for, and phase 4 publishes it with the same care as a better one.
- **The cited `google` comparator will sit at the old suite version.** Its rows carry classification `"2"` / translation `"1"` and the new local rows carry `"3"` / `"2"`. The items and the caps are byte-identical (no prompt is edited, `prompt_set_hash` is unchanged), so the scores remain comparable — but the version column will differ across a side-by-side table, and phase 4 must say why in the record rather than let a reader find it. Re-running google to align the version is rejected: it would pay cloud quota to regenerate identical answers to identical prompts.
- **`top_k: 0` may not mean "disabled" on the OpenAI-compatible endpoint.** It does on `/completion`, and the README lists the key as accepted, but "accepted" is not "same semantics". Phase 1 probes a two-request determinism check with the full pinned block before anything else is built; a divergence there changes `LOCAL_SAMPLING` and is recorded on the row, since every row publishes what it actually sent.
- **The truncation label changes underneath a separate open defect.** `finish_reason: "length"` is a correct cap signal, so local chat rows will finally report `truncated_max_tokens` where today's `stopped_limit` read publishes `unparseable` (`tech-debt.md`, 2026-09-06 `tiny-dense-models-alongside-moe`). That defect stays open for the runtime path and for any remaining `/completion` reader; this increment fixes it only where it migrates, and phase 2 says so in the changelog rather than silently closing someone else's row.
